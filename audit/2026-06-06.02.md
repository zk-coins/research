# zkCoins Specification — Logical Consistency Audit (Pass 2: verdict lens)

**Date:** 2026-06-06
**Snapshot:** [`zk-coins/docs@ac1d6e7`](https://github.com/zk-coins/docs/commit/ac1d6e7) — three further commits beyond the 2026-06-06.01 baseline (`527df18`), continuing the active hardening of the spec. (`e44f4c7` and `ac1d6e7` themselves resolve a MITM-via-proof-forwarding scenario in `access-explorer.md` §5.1 — exactly the class of issue this pass targets.)
**Scope:** the entire normative specification, re-baselined at HEAD.
**Method:** *the verdict lens* — for every normative rule that produces an accept/reject verdict for some party, ask **"would two honest verifiers, given the same Bitcoin chain, reach the same verdict?"** A "yes" means the rule is mechanically decidable. A "no" — or any room for two honest readers to disagree — is a finding.

This pass is the systematic complement to [`audit/2026-06-06.01.md`](./2026-06-06.01.md), which surfaced doc-set and crypto-derivation issues (F1–F5). Findings here are numbered **F6 onward**.

## Headline

One **high-severity** finding (F6) crosses four chapters: an ambiguity in the wording *"present on Bitcoin / anchored on Bitcoin"* in receive/anchor checks. Under the literal reading, a `SpendRecord` that §3.6 step 6 has **rejected** as a double-spend is still *"present in Bitcoin"* — so a receiver who checks presence only would credit a counterfeit output from a rejected record. The fix is wording: require **admission** under §3.6 step 6, not mere presence.

Five further findings refine the spec (F8, F9, F12, F13, F15). Two are documented properties more than defects (F10, F11). One liveness observation rounds out (F14). The other notable change in this pass: commit `e44f4c7` (PullChallenge → TLS-channel binding) already **closed** a MITM scenario the same lens would have surfaced — concrete evidence the methodology finds real things.

### F6 — *"present"* vs *"admitted"* `SpendRecord` ⚠️

The receive/anchor checks across four sections require the creating `SpendRecord` to be on Bitcoin, but use language (*"present in Bitcoin"*, *"anchored on Bitcoin"*) that does not require the record to have been **admitted** by [`onchain.md` §3.6](https://github.com/zk-coins/docs/blob/develop/docs/specification/onchain.md#36-chain-scanning) step 6 (the first-spend-wins gate).

**Disagreement scenario.** A spender double-spends their input coin `C`:
1. `SR1` publishes `nf(C)`, outputs include a real send to `R1`. `SR1` is admitted at canonical position 1.
2. `SR2` (later in canonical order) reuses `nf(C)` with a different output set (sends to `R2`, new change). `SR2` is **rejected** by §3.6 step 6 — its outputs are *"treated as never created."*
3. The spender delivers the `CoinProof` bundle for `R2`'s output off-chain. `R2` runs `proofs.md` §2.3.3:
   - Step 2 (proof verify): ✅ the proof was honestly computed; clauses 1–9 hold.
   - Step 3 (inclusion): ✅ `R2`'s coin is in `SR2.ocr`.
   - Step 4 (anchor): under the **literal "present" reading**, ✅ `SR2` is in Bitcoin and its nullifiers hash to `inr`.
   - Step 5 (own-nf non-membership): ✅ `R2`'s own future-spend nf isn't in the accumulator (`R2`'s coin hasn't been spent).
   - Step 6 (sanity): ✅.
4. `R2` credits the counterfeit. The input `C` has been spent **twice** in distinct downstream lineages.

The same ambiguity appears in:
- [`access-explorer.md` §5.6](https://github.com/zk-coins/docs/blob/develop/docs/specification/access-explorer.md#56-shareable-confirmation-links) step 4 — *"`output_coins_root`, that root's `SpendRecord` anchored on Bitcoin"*
- [`access-explorer.md` §5.7](https://github.com/zk-coins/docs/blob/develop/docs/specification/access-explorer.md#57-balance-attestation-history-private) — *"the `SpendRecord` at `anchor` … is **present** at `{block_hash, height}` on Bitcoin"*
- [`transport-recovery.md` §4.5](https://github.com/zk-coins/docs/blob/develop/docs/specification/transport-recovery.md#45-recovery) step 4 — *"the root is anchored in a real Bitcoin commitment"*

**Fix.** Replace *"present"* / *"anchored on Bitcoin"* with explicit language requiring **admission under `onchain.md` §3.6 step 6** (equivalently: the SpendRecord is in the verifier's locally-rebuilt admitted set, not merely in some Bitcoin block). The check then composes with §3.6: SR2 is in the verifier's rejected set, so step 4 fails — counterfeit blocked.

A subtle prerequisite: receivers must run §3.6 admission as part of normal verification (not just signature parsing). The spec already requires every node to rebuild the accumulator from the chain; making the rejected-record set first-class falls out for free.

### F8 — Empty `input_nullifiers_root` is not canonicalised

A mint spends no coin, so [`proofs.md` §2.3.1](https://github.com/zk-coins/docs/blob/develop/docs/specification/proofs.md#231-mint--issuance) line 90 sets `inr = the empty-set root`. [`onchain.md` §3.6](https://github.com/zk-coins/docs/blob/develop/docs/specification/onchain.md#36-chain-scanning) step 4 requires every scanner to *"recompute the Poseidon root over its listed `nullifiersⱼ` and check it equals the `inr`."* For `kⱼ = 0`, this requires a canonical value.

[`foundations.md` §1.4](https://github.com/zk-coins/docs/blob/develop/docs/specification/foundations.md#14-identifiers-and-hashes) defines `input_nullifiers_root` as *"Poseidon Merkle root over the transition's spent `nf`s, tag `NullifiersRoot`"* but does **not** specify the empty-tree root.

**Disagreement.** Implementer A picks `inr_empty = 0`. Implementer B picks `inr_empty = Hc("NullifiersRoot")` (zero-arg). They sign different `message = inr ‖ ocr` values for the same mint → A's mint records fail B's step 4 and vice versa. Cross-implementation interop blocker for the most common transition (mints).

**Fix.** Pin `inr_empty` explicitly in foundations §1.4 (and the analogous empty `ocr` root, which has the same shape but for outputs).

### F9 — `H(Pk₀)` check needs an out-of-band `Pk₀`

[`transport-recovery.md` §4.3](https://github.com/zk-coins/docs/blob/develop/docs/specification/transport-recovery.md#43-addressing-for-delivery) requires the sender to verify both the invoice's `op` signature **and** *"check that `H(Pk₀)` published by the recipient binds to address."* But the `Invoice` schema lists `{amount, recipient, asset_id, memo?, ivpk, op_pubkey, relays, sig}` — `Pk₀` is **absent**. Since `address = SHA-256(Pk₀)` and SHA-256 is preimage-resistant, the sender cannot derive `Pk₀` from `address`.

**Disagreement.** Two honest senders facing the same invoice: one consults Bitcoin to find a candidate `Pk₀` whose `H(Pk₀)` matches `address`, the other does not bother (no source specified) and skips the check, defeating its purpose. The spec leaves them silently inconsistent.

**Fix.** Either include `Pk₀` in the `Invoice` (sender then verifies `H(Pk₀) == address` directly), or specify the on-chain lookup procedure normatively (find an admitted `SpendRecord` whose `Pkᵢ` produces this address).

### F10 — *"Independent"* replica is not operationally verifiable (note)

[`transport-recovery.md` §4.6](https://github.com/zk-coins/docs/blob/develop/docs/specification/transport-recovery.md#46-data-availability--replication-factor-k) requires `k ≥ 2` (default 3) *"independent"* replicas — *"distinct operators/hosts; k copies on one operator do not count."* A sender has no protocol-level way to verify that two relays it doesn't run are not co-owned. The spec's mitigation is the recommended set (recipient's own + sender's own + at least one from the recipient's advertised set) — known parties with skin in the game. This is a pragmatic choice, not a defect, but the constraint is **trust-by-attestation**, not verifiable.

### F11 — Per-node revocation creates asymmetric verdicts (documented note)

[`access-explorer.md` §5.2](https://github.com/zk-coins/docs/blob/develop/docs/specification/access-explorer.md#52-view-grant) is explicit: *"A node a subject does not control cannot be compelled to honour a revocation; therefore grants SHOULD carry a short expiry."* Two honest nodes can disagree on whether a grant is revoked — by design. Not a defect; this finding is a marker that the verdict lens correctly flags it as inherent asymmetry, and the expiry-over-revocation guidance is the right mitigation.

### F12 — *"Latest"* state among multiple valid proofs is unspecified

[`architecture.md` §6.3](https://github.com/zk-coins/docs/blob/develop/docs/specification/architecture.md#63-node-portability-and-multi-node-operation) says the wallet *"MUST keep the answer that verifies and MAY ignore all others."* When **multiple** verifying answers come back — e.g. a stale-but-valid proof of an older `AccountState` and the current-state proof — the rule doesn't disambiguate.

**Disagreement.** Wallet A picks the answer with the higher `send_counter`; wallet B picks the first to verify. If a malicious node deliberately returns a stale-but-valid proof first, B may sign over an outdated state.

**Fix.** Specify that the wallet picks the verifying answer whose `new_account_state_hash` corresponds to the **latest admitted** `SpendRecord` signed under one of the wallet's own rotated `Pkᵢ` keys (which only the wallet can recognise on chain). This composes the §6.3 rule with F6's admission requirement.

### F13 — Mint authority and `cap_total` tracking are underspecified

[`architecture.md` §6.5](https://github.com/zk-coins/docs/blob/develop/docs/specification/architecture.md#65-issuance--trustless-permissionless-emission) requires the mint proof to verify *"the cumulative minted supply after this mint does not exceed `cap_total`."* This presupposes a **cumulative counter**. With Commitment-SMT/MMR removed (#21), the protocol has **no global per-asset supply commitment**.

Two ambiguities:
- **Who can mint?** [`proofs.md` §2.3.1](https://github.com/zk-coins/docs/blob/develop/docs/specification/proofs.md#231-mint--issuance) describes a single creator's flow (Wallet steps 1–3 use the creator's `sk₀`/`Pk₀`/`nk`), and `asset_id` commits to the creator's `Pk₀`. Yet §6.5 talks of *"open mints"* implying multi-party minting. Spec doesn't reconcile.
- **Where does the cumulative counter live?** If only the creator mints, their own `AccountState` can carry the counter (per-asset entry). If anyone can mint, there must be a shared, chain-derivable counter — but the only on-chain object is the `SpendRecord`, which does not carry `asset_id` (it's hidden in coin contents off-chain). A scanner can identify *mints* (records with `kⱼ = 0`) but cannot tell **which asset** each mint targets.

**Disagreement.** Verifier A interprets "creator-only mints" and validates against the creator's `AccountState` lineage. Verifier B interprets "permissionless mints" and asks for a shared counter — none exists — and either rejects all non-creator mints, or trusts an off-chain attestation. They disagree.

**Fix.** Decide and state explicitly: (a) creator-only mints, and the cumulative counter is per-creator-`AccountState` (current implicit reading), **or** (b) permissionless mints, and specify the on-chain mechanism for per-asset cumulative counting (would require additional public per-mint disclosure — e.g. an explicit `asset_id` or a deterministic mint-counter commitment in the `SpendRecord`).

### F14 — Half-aggregation collateral failure (note)

[`onchain.md` §3.3](https://github.com/zk-coins/docs/blob/develop/docs/specification/onchain.md#33-half-aggregation) and §3.6 step 3 specify that a failing multi-scalar check invalidates **every constituent `SpendRecord` of the failing batch**. A publisher that — accidentally or maliciously — bundles a single bad signature drops every honest signer in that batch. Permissionless publishing (§3.4) bounds the damage (signers retry via another publisher), but the per-batch *all-or-nothing* property warrants a note that honest senders may suffer collateral liveness impact and **MUST** be prepared to resubmit.

Not a verdict disagreement (every scanner agrees the batch is unconfirmed) and not a safety issue, so a note rather than a finding.

### F15 — Canonical verifier data location is not designated

[`proofs.md` §2.1](https://github.com/zk-coins/docs/blob/develop/docs/specification/proofs.md#21-the-compliance-predicate) clause 1: *"The verifier data MUST be fixed and identical in prover and verifier; a proof verified against any other verifier data is invalid."* Right requirement. The spec does not say **where this canonical verifier data is published and version-pinned**.

**Disagreement.** Two implementations adopt slightly different gate sets / parameters / circuit compilations from the same spec text; their verifier-data digests differ; they each consider the other's proofs invalid. The cyclic-recursion invariant (§2.2 *"the same circuit C"*) holds *within* one implementation but not *across*.

**Fix.** Designate a normative source for the canonical verifier data (e.g. a versioned reference artifact published alongside the spec, with its digest fixed in §1.1 or a new §1.8). This is essential for any future upgrade path.

## Cross-cutting: what `e44f4c7` already closed

Commit [`e44f4c7`](https://github.com/zk-coins/docs/commit/e44f4c7) ("bind PullChallenge to the TLS session, not an asserted server key") fixed precisely the kind of issue this lens surfaces. Old `chal` bound `server_id = node's op pubkey`; a malicious node `X` could relay a requester's OwnershipProof to honest node `Y`, and `Y` had no way to detect the relay (`op` is an account key, not a node identity). Two honest nodes literally returned different verdicts about *"is this OwnershipProof bound to me?"*. The new binding to the requester's authenticated transport channel (TLS-exporter or onion address) eliminates the relay path. Validates that the lens finds real, fix-worthy things.
