# D3 — Recovery and Operator Trust Surface

Concept-viability review, dimension D3 (project lead's highest-priority dimension).
Question: when nodes/operators fail, misbehave, or are switched, what actually
happens to a user's funds, state, and privacy?

Honesty mandate applies: this document states concrete failure modes with user
impact and does not soft-pedal. Where the spec is honest about a limit, that is
credited; where marketing language ("trustless", "no trusted operator") outruns
what the construction delivers for the realistic mass-market user, that gap is
named.

## Methodology

- **Primary source = the spec itself**, read against its own normative MUSTs:
  `specification.md` §1.2 (key hierarchy and custody split), §1.3 (per-coin
  keys), §4.1–§4.7 (transport, self-delivery, recovery, DA, privacy tradeoffs),
  §5.1–§5.4 (capability-gated pull, view grants, revocation), §6.1–§6.6 (node
  roles, wallet↔node, portability/multi-node, threat model, trust configs).
- **What the formal layer actually certifies** is taken verbatim from the
  Apalache package: `formal/property/P09_RecoveryCompleteness/{notes.md,
  certificate.txt}` and `formal/CERTIFICATE.md`. P9 is read for what it proves
  *and* for what it openly declines to prove.
- **Threat-model notes** (`notes/threat-model.md`, `notes/sss-trust-model.md`)
  are used for adversary framing. NOTE: these notes describe an *older* "SSS /
  Single Signer Server / bond-slashing" trust model that the current spec does
  **not** contain (the spec's only operator is the node holding `{ivk,ovk,op}`;
  there is no SSS, no bond, no slashing). The drift is itself recorded as a
  finding (R-D3-12) but the SSS mechanics are not treated as live.
- **Shielded CSV base construction.** The base paper's load-bearing custody
  assumption for this review is the one the spec restates in §4.5: the spendable
  *content* of a coin (its amount/value) lives **only** in the off-chain
  `CoinProof` bundle and is "choices others made; they exist only in the
  `CoinProof` bundles and cannot be derived from the seed or a hash." Recovery
  of value is therefore irreducibly a *data-availability* problem, not a
  key-derivation problem — this is the structural fact every walk-through below
  turns on. (PDF text-extraction tooling was unavailable in this environment;
  the custody assumption is cited through the spec's own §4.5 restatement rather
  than a page quote.)
- **Severity** = worst plausible user impact (Critical = silent fund loss /
  unrecoverable funds for a realistic user; High = recoverable only under
  conditions a normal user cannot guarantee, or a privacy break that
  de-anonymises the account; Medium = degraded UX / scoped privacy leak;
  Low = edge case or already mitigated).
  **Likelihood** = for the *realistic deployment* (young network, mostly
  foreign-node / hosted users), not for the idealised "everyone self-hosts" case.

Key structural facts established up front (they recur in every walk-through):

1. **`op`, `ivk`, `ovk` are fixed hardened derivations from the seed**
   (`A/1'/0'`, `A/1'/1'`, `A/2'`; §1.2). They do **not** rotate. The only way to
   change them is to change the **account** (`m/1798'/account'`), which changes
   the address — i.e. it is a *new identity*, not a key rotation. There is **no
   re-keying of an existing account.**
2. **Only the SPEND branch (`skᵢ`, `nk`) rotates** (`skᵢ` per transition). The
   viewing/transport keys an operator holds are permanent for the life of the
   account.
3. **The spend credential is data, not a key.** The bundle is "simultaneously
   the recipient's receipt and its spend credential" (Glossary, *Bundle*). Seed
   re-derivation restores keys; it does **not** restore the bundles. Recovery
   liveness is therefore gated on other operators still holding your data.

## Failure-mode walk-throughs

### 1. Worst-case operator outage — your own node dies permanently

**Trigger.** A self-hosted user's single node (holding `{ivk,ovk,op}` + the
bundle store / PostgreSQL + the prover) suffers total, unrecoverable loss (disk
death, fire, ransomware) **and** the operator's own durable backup (§4.5 primary
path) is also gone or never existed.

**What the user experiences, step by step (§4.5 emergency path).**
1. **Re-derive keys (step 1).** From the seed the wallet restores `A`, `ivk`,
   `dk`, `ovk`, `op`, `nk`, and the spend keys. This restores *identity and the
   ability to decrypt* — it restores **no value**. always works.
2. **Rebuild the public index (step 2).** Scan Bitcoin for `BatchInscription`s,
   fetch each `BatchBundle` from the relay mesh, verify the `AggregateBatchProof`,
   apply `prev_root → new_root`. This rebuilds the **global nullifier
   accumulator** — *if* a replica of every historical `BatchBundle` is still
   reachable. The spec admits the dead-end: "if every replica of a past
   `BatchBundle` has been lost, the operator … cannot reconstruct the member set
   of that batch."
3. **Pull candidate bundles (step 3).** Query the network's pull endpoints by
   `detect_tag` set or ownership proof. This is the load-bearing step: the
   incoming `CoinProof` bundles that carry your **balances** come back *only*
   here. The network is "an untrusted blob cache." **If no reachable node holds
   your bundle, it does not come back — full stop.**
4. **Verify (step 4) / rebuild AccountState (step 5).** Whatever comes back is
   verified against Bitcoin and folded into balances/`send_counter`/
   `current_pubkey`. Nothing forged is admitted (this is the part P9 certifies).

**Where it dead-ends for a *self-hosted* user.** §4.6 requires `k = 3`
replication to **independent operators** ("distinct operators/hosts; `k` copies
on one operator do not count"). For a lone self-hoster, "the recipient's own
node, the sender's own node, and at least one additional relay from the
recipient's advertised set" is the recommended replica set — but:
- The user's **own** node is replica #1 and it is the thing that just died.
- The **sender's** node is replica #2 — but the sender **MAY drop its copy after
  a valid ACK** (§4.2). For any coin received more than a short retention window
  ago, the sender is gone as a replica by design.
- The "additional relay from the recipient's advertised set" is replica #3 — for
  a lone self-hoster who advertised **only their own relay**, this collapses onto
  replica #1. There may be **no genuinely independent third holder at all.**
- **Self-delivered change/state bundles** (§4.2, normative) are the worst case:
  these are encrypted to the user's *own* IVPK and replicated to the user's
  *own* advertised set. A self-hoster who self-replicated only to their own
  infrastructure has `k = 1` in practice, violating §4.6's `k ≥ 2` MUST without
  ever being warned.

**Funds at risk?** YES. The most recent change coin / account-state bundle is
the spend credential for the *next* spend. If its only replicas were the dead
node, the account's spendable balance is **unrecoverable** — the seed cannot
re-derive it. This is the single sharpest edge in the whole design.
**Privacy at risk?** Not from the outage itself; from the *recovery* (see #4).
**Recoverable how?** Only if §4.6 was genuinely satisfied with independent
holders *and* those holders honour the pull. For a disciplined self-hoster with
real off-site replicas: yes. For the naive self-hoster: possibly never.
**Severity: Critical. Likelihood: Medium** (Low for users who run a correct
off-site replica; High for naive single-box self-hosters — and the spec gives
the wallet no MUST to *enforce* `k ≥ 2` independence at delivery time, only to
*claim* it).

→ **R-D3-1** (Critical/Medium): self-delivered change/state bundle can reach
effective `k = 1` for a self-hoster, making the live spendable balance
unrecoverable on node death despite seed backup.

### 2. Operator switch (planned) — move from node A to node B

**Trigger.** User decides to move from their own node A to a new own node B
(hardware upgrade), or from a foreign hosted node A to a foreign node B.

**Does the `op` key change?** **No.** `op = A/2'` is seed-derived and fixed
(structural fact 1). Node B, restored from the same seed, re-derives the
*identical* `op`, `ivk`, `ovk`. So:
- **Published invoices/profiles keep working.** They carry `op_pubkey = op·G`,
  unchanged. Good for portability (this is the §6.3 "no migration step"
  property, and it is real).
- **Pending ACKs addressed to the old `op` still verify** under B — same key.
- **Grants signed by the old `op` are still valid** — same `op`. The revocation
  *set*, however, is **node-local runtime state** (§5.2: "instructing the node(s)
  it controls"). When A dies, A's revocation set is gone; B starts with an
  **empty** revocation set and the user must re-issue every revocation on B.
  Any grant the user thought was revoked is live again on B until re-revoked.
  → **R-D3-7** (Medium/Medium): revocation state is per-node and is **not**
  reconstructed by the seed-only recovery (§4.5 rebuilds balances, not
  revocation sets); a node switch silently un-revokes previously revoked grants.

**The retained-key threat (the serious half).** Because `op`, `ivk`, `ovk`
**never rotate**, *switching away from operator A does not strip A of anything.*
A former operator A keeps a **permanent, full copy** of `{ivk,ovk,op}` for the
life of the account. With that retained bundle, a malicious or breached
ex-operator can, **forever, for every future transaction of that account**:
- **`ivk`** → derive `dk`, recognise the account's incoming coins by
  `detect_tag`, and **decrypt every future incoming `CoinProof`** (amounts,
  asset, sender-supplied data). Switching nodes does **not** stop this: new
  senders still encrypt to the same `IVPK = ivk·G`, and A still holds `ivk`.
- **`ovk`** → recover the plaintext of the account's outgoing coins.
- **`op`** → sign view grants and ACKs **as the account**, and act as the
  account's Nostr identity. A retained-`op` adversary can forge an `op` signature
  on a `ViewGrant` (the second invoice signature `sig` is `op`-signed; only
  `addr_sig` needs `sk₀`). It cannot forge an *invoice* that redirects funds
  (that needs `addr_sig` under `sk₀`, §4.3 check (ii) — correctly gated), but it
  can mint **read** grants over the account's data to third parties.

**The only true remediation is to abandon the account** (new `m/1798'/account'`
→ new address) and tell every counterparty the new address. There is **no key
rotation** that evicts a former operator. This is a structural consequence of
binding all viewing+transport keys to fixed hardened seed children with a 1:1
account↔address map (§1.2).

**Funds at risk?** No (custody is sound — A never had a SPEND key).
**Privacy at risk?** YES, permanently and retroactively-plus-prospectively: a
former operator reads the account's entire **future** financial history.
**Recoverable how?** Privacy is not recoverable for the old account; only
mitigable by migrating to a fresh account and never reusing the old address.
**Severity: High. Likelihood: Medium** (every hosted user who ever changes
provider, or whose old provider is later breached, is exposed).

→ **R-D3-2** (High/Medium): viewing/transport keys cannot be rotated; a former
or breached operator retains lifetime read access to all future account activity.
"Node portability" protects availability, **not** confidentiality against the
operator you left.

### 3. Malicious server state — stale/withheld answers, witness leakage, slow/wrong proving, stale-anchor equivocation

**Trigger.** A node the wallet uses is dishonest while still appearing to serve.

**(a) Withhold / stale-serve for correctness.** Covered well: §6.3 + P6 — the
wallet re-verifies every answer against Bitcoin and, under multi-node fan-out,
keeps the answer that verifies (the "≥1 honest node" property). A node cannot
make the wallet accept a forged state. Custody/correctness safe.

**(b) Witness-data leakage (the privacy hole behind the prover role).** The node
is **also the PROVER** (§6.1) and the holder of `{ivk,ovk}`. To build proofs and
to serve, it holds the **plaintext witness**: amounts, asset ids, the coin/
transaction graph for the account it serves. A malicious own-operator, or a
breached foreign operator, can **exfiltrate all of this out-of-band**. The spec
is honest at the config level — §6.6: "The node sees your plaintext" (own node),
"Plaintext disclosed to it" (foreign node). But the **marketing line "no trusted
operator" / "trustless" does not hold for privacy**: in the foreign-node case
(the realistic mass-market case, see #6) you trust the operator with the entire
private contents of your account, forever (compounded by #2). This is a privacy
trust, not a custody trust — but it is a *trust*, and a total one over the data
the product exists to hide.
**Quantify:** a foreign operator learns 100% of: per-coin amounts, asset mix,
full balance evolution, counterparty addresses that appear in your bundles,
and timing. It does **not** learn your spend keys. So the failure is
"surveillance by your provider", not "theft by your provider".
→ **R-D3-3** (High/High for foreign-node users): prover+`ivk`+`ovk` custody
means the serving operator has full plaintext view; "trustless" is true for
custody and false for privacy.

**(c) Griefing by proving slowly / wrong.** A node asked to *build* a proof can
stall or return garbage. A wrong proof is caught (the wallet verifies). A slow
or refusing prover is a **liveness** denial: the user cannot spend until they
switch to an honest prover. Portability (§6.3) is the escape hatch — but only if
another willing prover exists (see #7) and the user can move (#2's "switch is
free" property helps here). Self-delivery deadlock variant: if the prover that
must self-deliver the new state bundle stalls *after* inscribing the spend,
the user's next-spend credential may not be replicated (links to R-D3-1).
→ **R-D3-4** (Medium/Medium): a single prover can grief spend-liveness; mitigated
by node-switch only where an alternative honest prover is reachable.

**(d) Stale-anchor equivocation (serving an OLD state pre-signing).** F12 / §6.3
covers the *same-counter fork* (two verifying answers at the same
`send_counter` ⇒ wallet MUST stop). But a subtler attack: a node serves a
**genuinely-valid but stale** snapshot — a real prior `AccountState` at a *lower*
`send_counter` whose anchor is `completed` — and withholds the newer state. The
wallet's §6.3 rule is "select the highest `send_counter` among verifying
`completed` answers." A single-node user has **nothing to compare against**: the
stale state verifies, so the wallet builds the next transition on top of it. The
result is the user re-spending from an out-of-date view, producing a transition
that will be rejected (its input nullifiers already spent) or, worse,
constructing a self-conflicting parallel history at a counter the user already
advanced — which §6.3 then flags as a fork requiring manual resolution. So the
*safety* outcome (no theft) holds, but a malicious single node can **manufacture
the account-fork halt condition** as a denial-of-service, and a non-technical
user faces a scary "your account has forked — do not spend" state caused purely
by their operator lying. Multi-node fan-out defeats it (some honest node serves
the higher counter); a single-foreign-node user cannot.
→ **R-D3-5** (Medium/Medium): a single dishonest node can induce a stale-anchor
self-fork / spend-halt (DoS + alarming UX), not theft; only multi-node querying
mitigates, which hosted users typically do not do.

### 4. Recovery-flow leakage — what the serving node learns during emergency recovery

**Trigger.** User runs the §4.5 emergency path and queries nodes by `detect_tag`
set or ownership proof.

**Step by step what the queried node learns (§4.5 step 3 / §4.7):**
- **Pull by `detect_tag` set.** The user hands the serving node the full set of
  `detect_tag`s it is looking for. Because every coin has a distinct tag, the
  *cardinality* of that set ≈ the account's **entire incoming-coin count**, and
  the query timing/pattern reveals **when** recovery happened. The node learns
  "this requester is the owner of an account that received N coins" even if it
  cannot decrypt them. A node that *also* holds some of those bundles can now
  **link** the tag-set to the bundles it serves.
- **Pull by ownership proof.** The user signs a challenge with the identity key,
  i.e. **proves the address↔requester identity** to the serving node. The node
  now knows exactly which account is recovering and from what network location.

§4.7 acknowledges both ("Pulling by `detect_tag` reveals the tag-set to the
serving node; pulling by ownership proof reveals the requester's identity"). The
honesty is credited. But the privacy *cost differential* is real and large:
- **Normal operation:** your own node (holding `ivk`) does discovery silently;
  nothing about your tag-set or identity is exposed to anyone you don't already
  trust.
- **Emergency recovery:** to get your data back you must reveal the tag-set
  (≈ your incoming history size) and/or your identity to **whichever nodes
  happen to hold your bundles** — which, by §4.6's independence requirement, are
  operators you may **not** have a prior trust relationship with. Recovery
  therefore **broadcasts a recovery-identity signal to third-party operators.**

**Can a user recover *without* identifying themselves?** Only partially.
Pull-by-`detect_tag` avoids the explicit ownership signature, but the tag-set is
itself a stable fingerprint of the account (deterministic from `dk`), so two
nodes that both receive the tag-set can correlate that "the same account is
recovering across both." There is **no anonymous-recovery mode** (e.g. private
information retrieval, or oblivious bundle fetch) in the spec. A user who needs
their funds back after a disaster cannot get them without leaking either their
identity or their account fingerprint to the operators they must beg.
**Funds at risk?** No. **Privacy at risk?** Yes, scoped to the recovery event but
exposing account-size + identity to third-party operators.
**Severity: Medium. Likelihood: Medium** (only on emergency recovery, but that is
exactly when the user is most vulnerable and least able to choose who they ask).

→ **R-D3-6** (Medium/Medium): emergency recovery has no anonymous-retrieval mode;
it forces the recovering user to reveal account identity and/or incoming-history
cardinality to operators they may not trust. The privacy floor of recovery is
strictly worse than steady-state.

### 5. Off-chain backup privacy trade-off — `k`-replication of your whole account evolution

**Trigger.** Steady-state operation. Every self-delivered state bundle and every
incoming coin is, by §4.6, replicated to `k = 3` independent operators as
NIP-44 ciphertext.

**Assessment, honestly.**
- **Content confidentiality:** NIP-44 protects the *plaintext* against a replica
  that lacks `ivk`. A pure storage replica cannot read the coin.
- **Traffic analysis:** the replication graph is *not* hidden from the replicas.
  Who replicates to whom, when, and the bundle **sizes** are visible. A replica
  set that overlaps across many of your coins can profile your activity rate and
  link your bundles to one another by co-delivery timing even without
  decrypting. Tor (§4.7) hides IP but not the per-account replication pattern a
  cooperating replica set observes.
- **Key-compromise-later (the sharp one):** because `ivk` never rotates
  (structural fact 1), a **future** leak of `ivk` — by a breach of *any* node
  that ever held it, at *any* time — retroactively decrypts **every bundle that
  any replica still holds**, i.e. the account's *entire* history. The `k = 3`
  durability guarantee and the "retain indefinitely" rule for `BatchBundle`s
  (§4.6) mean these ciphertexts persist effectively forever, so the window for a
  later `ivk` leak to cash out the whole history is **unbounded**. There is no
  forward secrecy: one key, all history, forever.
- **Deletion impossibility:** these are **bearer ciphertexts replicated to
  independent operators**. There is **no revocation, no delete, no expiry** on a
  replicated `CoinProof`/`BatchBundle` (revocation exists only for *view grants*,
  §5.2, and even there only forward-only on nodes you control). A user can never
  cause their replicated history to be deleted. "Right to be forgotten" is
  structurally impossible.
**Funds at risk?** No. **Privacy at risk?** Yes — long-tail, catastrophic on a
later `ivk` compromise, and undeletable.
**Severity: High. Likelihood: Low–Medium** (requires a future `ivk` leak, but the
*impact* is total and the *window* is unbounded).

→ **R-D3-8** (High/Low-Medium): no forward secrecy on viewing keys + undeletable
replicated ciphertexts ⇒ a single future `ivk` compromise retroactively
de-anonymises the account's entire history with no possible remediation.

### 6. The op-key custody question, structurally — the foreign-node mass-market case

**Trigger.** The realistic mass-market user has **no infrastructure** and uses a
**foreign** node. §1.2 says: own node gets `{ivk,ovk,op}`; foreign node gets only
a scoped `op`-signed view grant. **But the foreign-node user must still receive
24/7 while their wallet is offline** (§6.1: "liveness does not depend on the
wallet"). To detect and decrypt incoming coins continuously, *something
always-on must hold `ivk`*. A view grant lets a node serve *already-decryptable*
data; it does **not** let a node that lacks `ivk` perform `detect_tag` discovery
or NIP-44 decryption of *new* deliveries (which are encrypted to `IVPK`). So a
foreign-node user who wants always-on receiving has exactly two options:
1. **Delegate `{ivk,ovk,op}` to the foreign node anyway** — at which point the
   "foreign node only gets a grant" protection evaporates and the operator has
   the full view bundle (= the own-node trust level, but the operator is now a
   *third party*). This is the de-facto mass-market deployment.
2. **Keep the wallet online to do its own `ivk` work** — which contradicts the
   thin-wallet / always-on-receiving premise and is unrealistic for a phone.

**State it plainly.** For the realistic non-infra user, **the operator holds
`ivk + ovk + op` = full lifetime view of the account + its transport identity.**
That is precisely the trust the marketing phrase "no trusted operator /
trustless" denies. §6.6 is honest at the sentence level ("Plaintext disclosed
to it"), but the **headline triad "Bitcoin-anchored · Shielded · Trustless"**
and the one-paragraph claim "no trusted operator" are **not honest for the mass
case**: the median user *does* trust an operator — with everything except the
ability to steal. The §6.6 trust-config table is *technically* accurate but
**buries the lede**: it presents "own wallet + own node" first and treats the
foreign-node row as a peer option, when the foreign-node row is the *default
reality* for anyone without a server. An end user reading the homepage would not
understand that "trustless" here means *theft-proof*, not *private-from-the-
operator*.
→ **R-D3-9** (High/High): for the realistic infra-less user, "trustless" is
misleading — the operator holds a full lifetime view (`ivk/ovk/op`). The trust
table is accurate but not framed honestly enough for non-technical users; the
default deployment is the *most*-trusting row, not the least.

### 7. k-replica "independence" in practice — bootstrap centralisation

**Trigger.** A young network. §4.6 MUST: the `k = 3` replicas are on **distinct
operators/hosts**; "`k` copies on one operator do not count."

**Reality at launch.** In a young network there are few independent operators.
The overwhelmingly likely bootstrap is **one service provider** (the project, or
the first popular host) running the node, the relay, *and* the archival replica —
i.e. `k = 3` *copies on one operator*, which **violates §4.6's MUST by default**.
The independence requirement is a paper constraint with no enforcement: nothing
in the protocol *checks* that the three replicas are independent operators (the
wallet cannot verify operator identity behind a hostname/cert — §5.1 even notes
the "one TLS terminator serving both" case it cannot distinguish). So early
users believe they have `k = 3` durability when they effectively have `k = 1`
correlated durability, and a single provider's failure or exit takes **all**
copies.
**Is this concept or ops?** Both, leaning ops/economics, but with a concept hole:
the spec mandates independence but provides **no mechanism to attest or verify
it**, so the MUST is unenforceable. That is a *concept* gap (missing
attestation), realised as an *ops* risk (bootstrap centralisation).
**Funds at risk?** Yes, transitively (collapses R-D3-1: if the one provider dies,
all replicas die ⇒ unrecoverable funds). **Privacy at risk?** Yes (one operator
sees everything ⇒ R-D3-3/9 with no diversification).
**Severity: High. Likelihood: High** (this is the *expected* state of any new
network).

→ **R-D3-10** (High/High): the §4.6 independence MUST is unenforceable and
unverifiable; the default young-network deployment is single-provider `k=1`
masquerading as `k=3`, undermining both recovery durability and privacy
diversification.

### Additional failure modes found

**8. Recovery during an ongoing reorg.** §4.5 step 4 requires accepting only
coins whose anchor is `completed` (≥6 confs) and unspent at `NAV(tip)`. If the
user recovers *during* a reorg shallower than the §6.6 5-block bound, the "tip"
view is in flux: a bundle that was `completed` may transiently regress, and a
nullifier's membership at `NAV(tip)` can flip. The spec's reorg bound makes this
*eventually* consistent, but a user who recovers and immediately spends inside
the finality window can anchor the new spend on a prev-state whose inclusion
block is later displaced — §6.3 acknowledges this for normal spends ("accepting
the reorg risk"), but recovery is exactly when a user is most likely to rush.
No recovery-specific guidance to wait for `completed` is given in §4.5.
→ **R-D3-11** (Medium/Low): recovery has no explicit "wait for finality before
the first post-recovery spend" rule; rushed recovery inside the reorg window can
produce a transition that the reorg invalidates.

**9. Stale accumulator view at recovery.** §4.5 step 2 depends on reaching a
replica of **every** historical `BatchBundle` to rebuild the accumulator. If some
old `BatchBundle` is unreachable (DA loss), the user can verify root *continuity*
on-chain but cannot reconstruct that batch's member set — and §4.6 warns an
unconfirmable batch "soft-forks the network." A recovering user who lands on a
node that itself never admitted a given batch (because *it* couldn't fetch the
bundle) inherits an incomplete accumulator and may wrongly treat one of their own
coins as spendable/unspent. Mitigated by the monotonic-replica-growth argument
(§4.6) for *admitted* batches, but not eliminated for genuinely DA-lost batches.
→ folded into R-D3-1 (DA loss) — no separate ID, but noted as a distinct
trigger.

**10. Partial bundle-store loss.** Between total survival and total loss, a node
can lose *some* bundles (partial disk corruption). The user's balance silently
loses exactly the coins whose only surviving replica was the corrupted region,
with **no error** — the account just appears to have a smaller balance, and the
user has no way to know a coin existed (the seed cannot enumerate received coins
independently of the bundles). Silent partial loss is more dangerous than total
loss because it is undetectable.
→ **R-D3-13** (High/Low-Medium): partial bundle-store loss silently reduces
balance with no detectable error; the seed provides no independent coin
enumeration to cross-check against.

**11. SSS / bond model drift in the notes.** `notes/threat-model.md` and
`notes/sss-trust-model.md` describe an "SSS / bond / slashing / 4-profile
finality" trust model that is **absent from the current spec**. If any reader
treats those notes as describing the shipping system, they will mis-assess the
operator trust surface (e.g. assume bond-slashing deters operator misbehaviour —
there is none). The shipping model has **no economic deterrent** on operator
misbehaviour at all; the only lever is "switch operators", which (per #2) does
not even revoke the old operator's view.
→ **R-D3-12** (Medium/n-a): documentation drift — the threat-model notes describe
a non-shipping SSS/bond design; the real operator surface has no economic
deterrent. Reconcile or clearly mark the notes as superseded.

## The operator trust surface

What each key/role lets an operator do — honest vs malicious. "Operator" =
the party running the node the user relies on (own node, or — the mass case —
a foreign/hosted node holding the delegated bundle).

| Key / role held | Honest operator does | Malicious / breached operator can do | Custody? | Privacy? | Rotatable to evict operator? |
|---|---|---|---|---|---|
| `ivk` (incoming view) | detect + decrypt your incoming coins so you receive 24/7 | read **every** past *and future* incoming coin (amounts, asset, sender data); link them; later-leak decrypts all replicated history | safe | **broken** — full incoming view, lifetime | **No** — fixed seed child; only a new account evicts |
| `ovk` (outgoing view) | reconstruct your outgoing-coin plaintext for display/recovery | read your outgoing coin plaintext | safe | **broken** — outgoing view | **No** |
| `op` (Nostr/identity) | relay your bundles, sign your ACKs + view grants | sign view grants over your data to third parties; act as your Nostr identity; forge ACKs | safe (can't spend) | enables further leakage | **No** |
| prover role + witness | build your validity proofs | exfiltrate witness plaintext (amounts, asset, tx graph) out-of-band; grief by slow/garbage proofs | safe | **broken** — full witness | n/a (any prover you use sees the witness) |
| relay / blob store | store + serve your bundles to `k` replicas | withhold (DoS / force emergency recovery); serve stale/old valid state (induce spend-halt fork); profile via traffic analysis; never delete replicated ciphertext | safe | metadata + denial | n/a |
| pull endpoint | serve your data only to valid capability | learn your identity (ownership proof) or incoming-history size (tag-set) at recovery | safe | recovery-time identity leak | n/a |
| revocation set | refuse revoked grants | (lost on node switch ⇒ silent un-revoke) | safe | stale grants reactivate | per-node, not seed-restored |
| **SPEND branch (`skᵢ`,`nk`)** | **never held by any node** | — | **safe** | — | — |

The single honest line — and it is genuinely strong — is the bottom row: **no
operator, however malicious, can spend, forge, or double-spend.** Custody is
cryptographically sound in every configuration, and P9's safety half proves the
recovery gate admits nothing forged. Every other row is a *trust*, and for the
foreign-node default it is a **total, lifetime, unrevocable privacy trust.**

## What P9's certificate does and does not cover

From `P09_RecoveryCompleteness/{notes.md,certificate.txt}` and `CERTIFICATE.md`.

**Covers (and covers well):**
- **No false-accept (SAFETY, UNBOUNDED).** The §4.5 step-4 verify gate is
  proven, by an inductive invariant valid in every reachable state, to admit
  **only** genuine own-bundles: `recovered ⊆ RealBundles`. A node returning a
  forged/unverifiable bundle — even one the wallet *can* decrypt (the modelled
  `AddressedForgeries` class) — is rejected. Own-key discipline and accumulator
  soundness fall out of the same invariant. This is exactly the "a node can only
  withhold, never forge" claim, mechanised. Credible and load-bearing.

**Does NOT cover (and openly says so):**
- **Liveness — i.e. that you actually get your funds back.** The genuine
  property `ConditionalLiveness == WF_vars(Recover) => <>[]( ∀ b ∈ RealBundles :
  b ∈ recovered )` is **unchecked**. Apalache 0.58.0 throws
  `NotImplementedError: Handling fairness is not supported yet`. The certificate
  substitutes an **enabledness surrogate** (`RecoverEnabledForHeld`: a held real
  bundle is *always gate-admissible*) — a *safety* stand-in, explicitly **not**
  the temporal liveness property. Graded **MEDIUM** by the audit.
- **Therefore P9 proves "recovery never accepts the wrong coin" but does NOT
  prove "recovery returns your coins."** The entire class of failure that
  actually loses user funds — **unavailability** (no reachable replica holds your
  bundle; all queried nodes collude/withhold; DA loss) — is **outside** the
  certificate. The notes are explicit: those executions "never satisfy the
  fairness premise — the audit's 'if all collude, the user is stuck.'"
- **Independence of replicas is assumed, not verified.** The model fixes
  `k`-replication as a parameter; it does not (cannot) model whether the three
  replicas are *genuinely independent operators* (R-D3-10). The MEDIUM label, in
  the audit's own words, "depends on `k` and operator independence."

**Bluntly:** P9 certifies the part of recovery that protects *Bitcoin* (no
forged credit) and leaves uncertified the part that protects the *user* (getting
their money back). For dimension D3 — "what happens to a user's funds when
operators fail" — the certified property is the *less* important half. The
funds-loss modes (R-D3-1, R-D3-10, R-D3-13) live entirely in the uncertified
liveness/availability gap, and that gap is real, not a tooling artefact: even
with a perfect fairness checker, "all replicas lost ⇒ funds gone" is true by
construction (§4.5: value "cannot be derived from the seed").

## Recommendations

1. **Enforce `k ≥ 2` independent replication at the wallet, with a hard
   pre-spend gate** (addresses R-D3-1, R-D3-10, R-D3-13). The wallet MUST NOT
   report a received/changed balance as "safe" until it has *confirmed* the
   bundle is held by ≥2 holders the wallet treats as independent, and SHOULD
   surface replica count in the UI. Today the independence MUST is operator-side
   prose with no client enforcement — the one rule that prevents silent fund loss
   is the one rule nothing checks.

2. **Add a replica-independence attestation mechanism** (R-D3-10). Without a way
   for a wallet to *verify* that three hostnames are three operators (signed
   operator identities, distinct on-chain bonds, or at minimum distinct
   long-term keys the wallet can pin and diversify over), the independence MUST
   is unfalsifiable and the young-network default silently degrades to `k=1`.

3. **State the operator privacy trust honestly in user-facing material**
   (R-D3-3, R-D3-9). Replace/qualify "trustless" and "no trusted operator" with
   the precise claim the construction supports: **"your operator cannot steal
   your funds; in the hosted configuration your operator can see your full
   transaction history."** The §6.6 table is accurate — promote its foreign-node
   row to the *default* framing for non-infra users.

4. **Provide a viewing-key rotation / operator-eviction story** (R-D3-2,
   R-D3-8). The current answer — "abandon the account and tell everyone your new
   address" — is unacceptable for a normal user changing providers. Investigate
   diversified incoming-view keys (so a per-operator `ivk` can be retired) or at
   minimum document migration as a first-class, guided flow with the privacy
   consequence spelled out.

5. **Add an anonymous / oblivious recovery-retrieval option** (R-D3-6).
   Pull-by-tag-set leaks incoming-history cardinality; ownership-proof leaks
   identity. A PIR-style or oblivious bundle fetch, even as a future version,
   would close the "you must dox yourself to the operators you beg" gap that
   bites users at their most vulnerable moment.

6. **Fix the revocation-loss-on-switch hole** (R-D3-7). Either fold the
   revocation set into seed-recoverable state, or make revocation
   `expiry`-first (the spec already SHOULD-recommends short expiries — make it a
   MUST for any grant the user might want to revoke) so a node switch cannot
   silently reactivate stale grants.

7. **Add recovery-time finality guidance** (R-D3-11): a normative "wait for
   `completed` (≥6 confs) before the first post-recovery spend" rule in §4.5.

8. **Reconcile or retire the SSS/bond threat-model notes** (R-D3-12) so no
   reader mistakes a non-shipping economic-deterrent design for the current
   operator surface.

## Verdict

**Custody:** strong and honestly certified — no operator can steal, forge, or
double-spend, in any configuration, and P9 proves recovery never credits a
forged coin. That half of the story is genuinely good.

**Recovery + operator trust for non-technical users: NO — conditional at best.**
The certified property protects Bitcoin, not the user's funds; the funds-loss
modes (silent `k=1`, single-provider bootstrap, partial/total bundle loss) live
entirely in the *uncertified* availability gap and are the *expected* state of a
young network. And the privacy story for the realistic infra-less user directly
contradicts the "trustless / no trusted operator" headline: the hosted operator
holds an unrotatable, lifetime, undeletable full view of the account. **As it
stands the recovery/operator story is not strong enough for non-technical users;
it becomes conditionally acceptable only if Recommendations 1–4 are
implemented** (client-enforced independent `k`-replication, an independence
attestation, honest privacy framing, and a viewing-key/operator-eviction path).
