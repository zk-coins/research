# D7 — Scaling Concept

Concept-viability review, dimension **D7: scaling concept** of the
aggregator / accumulator scheme. The question: is the design conceptually
scalable, what are its implicit assumptions about coin counts, transactions per
day, and recovery load, what does the per-send input cap mean for throughput,
and what breaks at 10x / 100x / 1000x.

Baseline: `docs/docs/specification.md` (post-`docs#40` single-page spec),
cross-referenced with the project's own throughput statements
(`research/primary-sources/zkcoins-gist.md`, `research/notes/l2-protocol-design.md`,
`docs/docs/comparisons.md`, `docs/docs/risks.md`) and the two sibling reviews
that already touch throughput (`D2.md` R-D2-5, `D4.md`). Where this review
overlaps those, it defers the *correctness* framing to them and supplies the
*quantitative envelope* they explicitly leave to "the D7 scaling review".

---

## Methodology + assumptions

This is a concept-viability analysis, not a benchmark. Every number below is an
**order-of-magnitude envelope** derived from the spec's own constants plus a
small set of explicitly stated assumptions. Numbers are labelled **[spec]**
(read directly from the specification), **[project]** (stated in the project's
own notes), or **[est]** (my estimate, with the assumption named). The goal is a
defensible ceiling and its sensitivity, not a precise figure.

**Constants read from the spec (all [spec]):**

- One `BatchInscription` per accumulator state transition, **231 bytes / ~58
  vBytes, constant in batch size** (§3.1, §3.5, §3.8).
- The accumulator advances **strictly sequentially**: each inscription's
  `prev_root` MUST equal the most-recently-admitted `new_root`; competing
  publishers on the same `prev_root` are resolved by Bitcoin canonical order and
  the loser is rejected as stale (§3.4 sequential-commitment, §3.6 step 4).
- Bitcoin cadence: ~144 blocks/day, 6-confirmation finality, ≤5-block reorg
  assumption (§3.9). (~144 blocks/day is standard Bitcoin, used as [spec-adjacent].)
- `AggregateBatchProof` is **constant-size in `m`** (~100 KB floor), recursive
  over `m` member proofs; "proving time scales sub-linearly in `m`" (§2.2,
  §3.4). Each **member** proof is a per-account recursive PCD that verifies that
  account's transition.
- Accumulator = **256-depth sparse Merkle tree**, one leaf per nullifier ever,
  **cannot prune** populated paths; only never-occupied key space is free
  (§1.7.6, §3.7 "Storage").
- Light-client Path B: SMT path ≈ **512 bytes/query** (§3.7); Path A holds the
  full `nf` set (~32 bytes/`nf` + indexing).
- `CoinProof` and `BatchBundle` bundles are **~100 KB**, `k = 3` replicated,
  retained **indefinitely** by every scanner that admits a bundle (§4.2, §4.6).
- Detection is **not server-side filterable**: a recipient pulls the full
  candidate delivery-event set and runs one Poseidon hash per candidate;
  fuzzy message detection (FMD) is an OPTIONAL bandwidth upgrade only (§4.4,
  §4.7).

**The per-send input cap (MAX_IN_COINS = 8).** The spec does not name a numeric
cap in the snapshot reviewed (the `SpendRecord` carries `k: u8` input
nullifiers, §1.4, which is structurally unbounded at u8 = 255). Per the review
brief, **the project's own performance work fixed MAX_IN_COINS = 8** as the
per-send input cap, on the grounds that the 8-source recursion dominates
send-proving cost. I treat **MAX_IN_COINS = 8 [project]** as the working
assumption throughout, and flag the spec/implementation gap as a finding
(R-D7-6). All fragmentation reasoning below is stated as a function of this cap
and re-derivable for any other value.

**Estimation assumptions (all [est], named at use):**

- E1 — *batch proving time*: I assume a mature single-host CPU prover (the spec's
  stated production model, §risks "CPU-only on a single Apple Silicon host")
  takes on the order of **seconds to tens of seconds** to build one
  `AggregateBatchProof`, consistent with `D2.md`'s "seconds to tens of seconds"
  and the project's R2 warm baseline. I use **10 s/batch** as the central
  estimate, with a **1 s** optimistic and **60 s** pessimistic bracket.
- E2 — *records per batch `m`*: bounded by (a) proving wall-clock budget per
  batch slot and (b) bundle size/DA bandwidth, not by anything on-chain. I use
  **m = 100** central, **m = 1 000** optimistic, **m = 10** pessimistic — the
  exact range the spec itself uses in its cost examples (§3.5, §3.8).
- E3 — *base load*: I anchor "1x" at **1 M tx/day ≈ 11.6 tx/s**, roughly the
  project's stated "hundreds to low-thousands of TPS" target ceiling
  (`notes/README.md`, `notes/l2-protocol-design.md`) taken at its low end. 10x /
  100x / 1000x are then 10 M / 100 M / 1 B tx/day.
- E4 — *years of operation*: storage/growth envelopes use **Y = 5 years** unless
  stated.

## Scaling-envelope analysis

### 1. Throughput ceiling from the sequential accumulator

**The hard structural limit.** Because the accumulator advances one batch per
admitted inscription and each inscription chains `prev_root → new_root`
sequentially (§3.4, §3.6 step 4), **the global transaction rate is
(batches that can land per unit time) × (records per batch `m`)** — and the
first factor is gated by Bitcoin ordering, not by how many publishers exist.

**Can more than one batch land per block?** Yes, in principle: §3.6 step 4 makes
the ordering key `(block height, reveal-tx index within the block)`. Multiple
reveal transactions in one block can each carry a `BatchInscription`, and they
are totally ordered by tx-index, so a chain of `prev_root → new_root`
transitions **can** be satisfied *within* a single block — **but only if each
later inscription in the block already commits to the `prev_root` that the
earlier in-block inscription produces.** That requires the publishers to
*coordinate* (one must know the other's `new_root` before building its proof and
choosing its tx position), which defeats the permissionless-race model: two
*independent* publishers racing on the same `prev_root` in the same block still
produce only **one** winner (§3.4). So:

- **Uncoordinated (the spec's permissionless default): ~1 successful batch per
  block.** Ceiling = `144 batches/day × m`.
- **Coordinated batch-chaining within a block:** in theory many per block, but
  this is a *single sequencer in disguise* — it reintroduces the coordinator the
  design removed, and is not specified. I treat it as out-of-envelope.

**Defensible global ceiling (uncoordinated, [est] on m):**

| `m` (records/batch) | tx/day = 144·m | tx/s |
|---|---|---|
| 10  (pessimistic) | 1 440      | 0.017 |
| 100 (central)     | 14 400     | 0.17 |
| 1 000 (optimistic)| 144 000    | 1.67 |
| 10 000 (aggressive)| 1 440 000 | 16.7 |

**Reading this honestly.** To reach the project's own **1 M tx/day** target the
design needs **m ≈ 7 000 records per batch, every block, with no contention
waste**. That is the optimistic edge of E2 *and* assumes zero stale-reproving
loss — which §3.4/§3.6 and `D2.md` R-D2-5 say is *not* the steady state under
contention (under `P` competing publishers, up to `(P−1)/P` of in-flight proofs
are wasted). The realistic central envelope is **~14 000 tx/day (~0.17 tx/s)**,
two orders of magnitude below "hundreds of TPS."

**Sensitivity.** The ceiling is *linear in `m`* and *linear in batches/block*.
`m` is the only lever that does not require breaking the permissionless model,
and `m` is itself capped by E1 (proving wall-clock) and bundle DA (§3 below). So
throughput is **proving-bound, then DA-bound, with a hard sequential gate on top**.

> The original zkCoins throughput claim (104 tx/s, `zkcoins-gist.md`) and the
> "PayPal-surpassing" framing were computed under a **pre-`docs#40`** model where
> each spend put a ~64-byte *seal/nullifier* on chain and throughput was bounded
> by **on-chain bytes** (4 MB / 10 min / 64 B). The post-#40 redesign moved
> nullifiers **off-chain** (constant 231-byte batch inscription, records hidden),
> which *removes* the on-chain-bytes bound but *replaces* it with the
> **sequential-accumulator + proving** bound analysed here. The two ceilings are
> not comparable, and the headline 104 tx/s no longer characterises the shipped
> design. `comparisons.md` still states "Capacity: bounded by Bitcoin L1 (one
> compact commitment per TX)" — that line is pre-#40 and is now wrong in both
> directions (it is no longer per-TX, and the binding constraint is no longer L1
> capacity). See R-D7-1.

### 2. Proving as the bottleneck

`AggregateBatchProof` is "constant-size in `m`" but **not constant-time in `m`**:
the proof *size* asymptotes to the ~100 KB recursion floor, while the proving
*time* carries a per-member contribution (one in-circuit signature check + one
SMT-insertion step folded into the recursion, §2.2 clause 3–4, §3.8). "Sub-linear
in `m`" refers to recursion overhead amortisation, **not** to the per-member work
vanishing.

Two nested cost layers:

1. **Member proof (per spend).** A per-account recursive PCD that, with
   MAX_IN_COINS = 8 [project], verifies **up to 8 input-coin** spends. The
   project's own perf work flagged this **8-source recursion as the dominant
   cost per send**. A spend consuming 8 coins is the heavy case; a 1-input spend
   is cheap. This cost is borne by the *spender* (or its prover-node), once per
   send, before the record reaches a publisher.
2. **Aggregate proof (per batch).** The publisher recursively verifies `m`
   member proofs + `m` SMT insertions inside one proof. This is borne by the
   *publisher*, once per batch.

**Realistic m and cadence.** Given E1 (10 s central per batch) and the §3.4
"bounded interval" batching guidance, a publisher that wins ~1 slot/block has
**~6–10 minutes between its successful inscriptions** — ample wall-clock to build
a *large* batch. So proving time per se does **not** cap `m` at the per-block
cadence; **bundle size and DA bandwidth do** (§3). The binding proving constraint
is instead the **contention re-proving tax** (§1, R-D2-5): every time a
competitor lands first, the publisher's in-flight aggregate proof is stale and
the seconds-to-tens-of-seconds of work is **wasted**. Under load this turns
"sub-linear in `m`" from a virtue into a liability — the bigger the batch you
were building, the more you lose when sniped.

**Net:** proving is the *spender-side* bottleneck for heavy 8-input sends and the
*publisher-side* griefing surface under contention; it is **not** the raw
throughput ceiling (that is the sequential gate × `m`). It *is* what makes
small/altruistic publishers uneconomic (cf. `D4.md`: professionalisation into an
oligopoly).

### 3. Accumulator growth (storage + path-proof cost)

The accumulator is **one leaf per nullifier ever admitted, unprunable** (§3.7).
Total nullifiers ≈ total spends (each spend admits `k_j` nullifiers; with
MAX_IN_COINS = 8 and an [est] average of ~1.5 inputs/spend, ≈ 1.5 `nf` per tx).

**Per-node state (Path A).** ~32 bytes/`nf` + indexing; I use **~64 bytes/`nf`
effective** [est] including index overhead. Bundle DA is the dominant term:
every admitted `BatchBundle` (~100 KB) is retained **indefinitely** by every
scanning node and `k = 3` replicated (§4.6). Total bundle volume ≈
`(tx / m) × 100 KB`, and it is **forever**.

Take base = 1 M tx/day = 365 M tx/yr; Y = 5 yr → 1.825 B tx; ~2.7 B `nf` [est].

| Scale | tx/day | nf set (5 yr) | Path-A nf index | Bundle DA total (5 yr, m=100, ×k=3) |
|---|---|---|---|---|
| 1x   | 1 M   | ~2.7 B   | ~175 GB  | ~27 PB |
| 10x  | 10 M  | ~27 B    | ~1.7 TB  | ~270 PB |
| 100x | 100 M | ~270 B   | ~17 TB   | ~2.7 EB |
| 1000x| 1 B   | ~2.7 T   | ~175 TB  | ~27 EB |

(Bundle DA total = `tx/m × 100 KB × k`. At m=1 000 it is 10× smaller; the table
uses the central m=100. Even at m=1 000, 1x = ~2.7 PB and 100x = ~270 PB over 5
years — still unprunable and growing.)

**Where it breaks.**

- **Path-A node storage** is *not* the first thing to break: the bare `nf` index
  (≤175 TB at 1000x) is large but within data-centre reach. **Bundle DA total
  volume is the real wall** — petabytes-to-exabytes of *unprunable*, *k=3*,
  *every-scanner-retains-it* data even at the 1x base. The §4.6 long-term-retention
  rule ("every admitting node MUST retain indefinitely") means this grows
  monotonically with both history *and* node count, with **no GC story** (the
  spec explicitly defers pruning to "a future version").
- **Path-B light clients** scale *fine* on storage (231 B/batch of on-chain roots
  + 512 B/query), which is the design's saving grace — but they depend on a
  Path-A node existing to answer queries, and Path-A nodes are exactly what
  becomes uneconomic at scale. **A network where nobody can afford to be Path-A
  has no one to serve Path-B.**

**Verdict:** accumulator *leaf* growth is survivable; **bundle DA growth is not
sustainable past a niche** without a pruning/archival design that does not exist
yet. This is the quietest and most fundamental ceiling.

### 4. Recovery load

Emergency recovery (§4.5) is, in the worst case, **a full re-scan of all of
Bitcoin's zkCoins history**: for every admitted `BatchInscription`, fetch its
`BatchBundle`, verify its `AggregateBatchProof`, apply the root transition (step
2), then pull the user's own candidate bundles and re-verify each recursive proof
(steps 3–4).

Cost ≈ `O(total batches) × (bundle fetch + aggregate-proof verify)` +
`O(user's lifetime coins) × (per-coin recursive verify)`.

- The **per-batch verify** is one recursive-proof check (~100 KB proof, fast to
  *verify* even though slow to *prove*) plus a ~100 KB bundle download. At 1x /
  5 yr that is `1.825 B tx / 100 = ~18.3 M batches` to fetch-and-verify — at
  ~100 KB each that is **~1.8 TB of download and ~18 M proof verifications** for a
  *single* cold recovery. At 100x: ~1.8 B batches, **~180 PB**, ~1.8 B verifies.
- The **per-user** term scales with that user's own activity, which is small;
  the killer is the **global** rebuild term, which scales with *everyone's*
  history because the accumulator is global and unprunable.

**Is recovery feasible at 100x?** **No, not as a from-seed cold recovery.** At
100x a cold rebuild is a multi-hundred-petabyte, billion-verification job — only
the §4.5 *primary* path (the node's own local backup) is viable, which means
**recovery viability collapses onto "did you keep your own backup", i.e. the
exact assumption the trustless emergency path was meant to remove.** The spec is
honest that emergency recovery is the *fallback*; D7's contribution is that the
fallback is **only** viable at niche volume, and that this *reintroduces a
custody-availability dependency at scale* (cross-ref `D3.md` recovery surface).

### 5. Detect-tag scan

Detection is recipient-side and **not server-filterable** (§4.4): the recipient
pulls the candidate delivery-event set in full and runs one Poseidon hash per
candidate. The candidate set per recipient grows with **total global delivery
traffic**, because the relay cannot pre-filter without `dk` and the design
explicitly chose deterministic per-coin tags over FMD by default (§4.7).

**Quantify.** Each tx produces ≥1 delivery event (≥1 output coin to a
counterparty, plus a self-delivered change coin per §4.2). So global delivery
events ≈ **~2× tx/day** [est]. A mobile recipient that pulls "its relay set" must,
in the worst case, scan a slice proportional to that relay's share of *all*
traffic.

| Scale | delivery events/day [est ~2×tx] | events/s | one Poseidon-hash/event |
|---|---|---|---|
| 1x   | ~2 M    | ~23/s    | trivial |
| 10x  | ~20 M   | ~230/s   | OK on a phone |
| 100x | ~200 M  | ~2 300/s | painful: ~200 M hashes/day to stay synced |
| 1000x| ~2 B    | ~23 000/s| infeasible on mobile (CPU *and* bandwidth) |

The wall is **bandwidth**, not CPU: the recipient must *pull* each candidate
event's metadata even though it discards non-matches after one hash. At 100x a
phone synchronising a day of global traffic is downloading and scanning hundreds
of millions of events. **The OPTIONAL FMD upgrade is not optional at scale** — it
is a *hard requirement* beyond ~10x for mobile viability, because it is the only
mechanism that lets a relay return a *small* candidate set without learning the
recipient. The spec correctly identifies FMD as the lever but mis-frames it as a
mere "scan-efficiency upgrade"; at >10x it is load-bearing. See R-D7-4.

(A partial mitigation the spec already has: a recipient can scope to its own
*advertised relay set* rather than all relays, so it scans only that relay's
slice. But that slice still grows with global traffic on a popular relay, and
narrowing the relay set narrows the anonymity/cover-traffic set — a privacy/scan
tradeoff, not an escape.)

### 6. Coin fragmentation (the MAX_IN_COINS = 8 consolidation tax)

With MAX_IN_COINS = 8 [project], a single send can consume **at most 8 input
coins**. An account that *receives* `N` separate coins and wants to spend their
combined value in one payment cannot, if `N > 8`: it must first **consolidate**,
and consolidation is itself a send (8-into-1), each consuming an on-chain batch
slot and a 6-confirmation wait.

**The tax, walked.** To collapse `N` coins down to a spendable handful takes
`⌈log_8 N⌉` rounds of 8-into-1 consolidation (each round divides the coin count
by ~8), or `⌈(N−1)/7⌉` sends if done greedily one merge at a time:

| Coins received `N` | greedy sends to consolidate to 1 | rounds (log_8) |
|---|---|---|
| 8    | 1   | 1 |
| 64   | 9   | 2 |
| 512  | 73  | 3 |
| 4 096| 585 | 4 |

**Why this is a *scaling* tax, not just a UX wrinkle.** Each consolidation send
is (a) a member record competing for the **sequential accumulator slot** (§1), (b)
an **8-source recursive proof** — the *most expensive* member proof (§2), and (c)
a 6-conf, ~hour-latency on-chain event. So **the more active a receiver is, the
more of the scarce global throughput it must consume on housekeeping that
produces no payment.** A merchant taking many small payments is precisely the
high-volume actor the design most needs to support, and it is precisely the actor
this tax penalises hardest. At system scale, consolidation traffic competes with
real payment traffic for the *same one-batch-per-block* gate — fragmentation
*amplifies* the throughput ceiling problem rather than being orthogonal to it.

**Sensitivity to the cap.** The tax is `log_(cap) N`; raising the cap to 16 or 32
softens it but *raises per-send proving cost* (more sources in the recursion),
trading the fragmentation tax for the proving tax. There is no free setting:
small cap → fragmentation tax; large cap → proving tax. MAX_IN_COINS is a genuine
throughput *dial*, and 8 is a middle setting whose consequences the spec does not
analyse. See R-D7-5, R-D7-6.

## What breaks first

Ranked, soonest ceiling first:

1. **Sequential accumulator throughput (breaks earliest).** One batch per
   accumulator tip, ~1 successful uncoordinated batch per Bitcoin block. To clear
   even the 1x = 1 M tx/day target the design needs `m` in the **thousands per
   batch every block with zero contention waste** — the optimistic edge of every
   assumption at once. Realistic central envelope is **~14 000 tx/day (~0.17
   tx/s)**. This is the headline ceiling and it is *intrinsic* (it is what makes
   first-spend-wins a clean total order — see `D2.md` R-D2-5). **Rank 1.**
2. **Detect-tag scan on mobile (no FMD).** Becomes painful at ~10x and infeasible
   at ~100x; bandwidth-bound, not CPU-bound. **Rank 2** for the *user-visible*
   experience.
3. **Bundle DA total volume (unprunable, k=3, retained-forever).** Already in the
   *tens of petabytes over 5 years at 1x*; the most *fundamental* long-term wall
   because there is no pruning design at all, but it degrades gradually rather
   than failing at a sharp threshold. **Rank 3** by urgency, **Rank 1 by
   irreversibility.**
4. **Cold recovery cost.** Collapses onto "keep your own backup" past ~10–100x.
   **Rank 4.**
5. **Proving / contention.** Caps publisher economics and grief-resistance well
   before it caps raw throughput; mostly a *centralisation* pressure (cf.
   `D4.md`) rather than a hard ceiling. **Rank 5.**
6. **Path-A `nf` index storage.** The *least* binding — data-centre-scale even at
   1000x. **Rank 6.**

The throughput ceiling and the DA-volume ceiling are the two that no amount of
hardware fixes: one is a logical serialization point, the other is unbounded
unprunable retention.

## Comparison to the design's own stated goals

- **"Throughput scales to hundreds of TPS … surpasses PayPal"** (`zkcoins-gist.md`):
  this was the **pre-#40 on-chain-bytes** model (104 tx/s from 4 MB/10 min/64 B).
  The shipped post-#40 design's *central* envelope is **~0.17 tx/s** and its
  optimistic edge **~1.7 tx/s** (m=1 000, 1 batch/block). The headline goal is
  **off by ~2–3 orders of magnitude** against the design as specified. The
  `comparisons.md` "bounded by Bitcoin L1 (one compact commitment per TX)" line
  is stale and contradicts §3.1's constant-size-per-*batch* model (R-D7-1).
- **"Hundreds to low-thousands of TPS, not Hyperliquid-scale"** (`notes/README.md`,
  the *honest internal* target): even this low bar requires `m ≈ 7 000–70 000`
  records per block with no contention loss — achievable only with a coordinated
  single-sequencer batch-chain, which contradicts the permissionless-publisher
  principle. The internal target is **directionally right (not Hyperliquid) but
  still ~1–2 orders optimistic** for the permissionless model.
- **"Self-hostable node" (Requirement 7) + "node portability" (Requirement 10):**
  in tension with the unprunable bundle-DA growth (§3). A self-hosted node that
  honours the §4.6 retain-forever rule faces petabyte-scale storage at modest
  global volume; portability of that state is then non-trivial. The requirements
  are met at low volume and **erode at scale**.
- **"Recovery" (Requirement 6):** the emergency path is feasible at niche volume
  and **backup-dependent at scale** (§4) — the trustless cold path is the first
  casualty of growth.

The design's *correctness* properties (no-double-spend, privacy, trustlessness)
are scale-invariant and well-verified elsewhere in this review set. Its
*performance* goals, as publicly stated, are **inherited from a superseded model**
and not re-derived for the current spec.

## Recommendations

1. **Restate the throughput ceiling for the post-#40 design.** Replace the
   `zkcoins-gist.md` 104-tx/s claim and the `comparisons.md` "bounded by Bitcoin
   L1 / one commitment per TX" line with the real binding constraint:
   `throughput = (batches/block) × m`, gated by the sequential accumulator.
   Publish an honest central envelope (~10⁴ tx/day order) and the assumptions
   behind any larger figure. (Addresses R-D7-1.)
2. **Specify the publisher-coordination / prev_root-leasing scheme** that `D2.md`
   and `D4.md` both call for. The only way past ~1 batch/block without a hidden
   sequencer is an explicit, permissionless-compatible coordination protocol; its
   absence is *the* throughput blocker. (R-D7-2.)
3. **Design the bundle-DA pruning/archival story now, not in "a future
   version".** Unprunable k=3 retained-forever 100 KB bundles are the
   irreversible long-term wall. Options: erasure-coded archival tiers, epoch
   checkpoints that let nodes drop pre-checkpoint bundles, or accumulator
   snapshotting. (R-D7-3.)
4. **Promote FMD from OPTIONAL to REQUIRED-beyond-niche** for mobile detection,
   and state the volume threshold at which the deterministic scan stops being
   viable (~10x in this analysis). (R-D7-4.)
5. **Analyse MAX_IN_COINS as a throughput dial.** Document the cap, its
   fragmentation-vs-proving tradeoff, and a consolidation strategy for
   high-receive accounts (e.g. background auto-consolidation, larger cap for
   merchant nodes). (R-D7-5.)
6. **Pin MAX_IN_COINS in the spec.** It is currently an implementation constant
   (`k: u8`, structurally ≤255) with a project-asserted value of 8; a
   throughput-and-fragmentation-defining parameter must be normative. (R-D7-6.)
