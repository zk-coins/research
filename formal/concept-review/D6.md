# D6 — End-to-End UX Walk-throughs

Concept-viability review, dimension D6.
Question: play the key user journeys concretely. Per journey — what assumptions
must the user accept, what happens when things go wrong, and is this realistic
for an actual end user? The honesty mandate applies: where a journey is
unworkable for a non-technical user, this document says so plainly. Where the
spec is honest about a limit, that is credited.

This is a **UX-adoption** review, not a security review. "Severity" below =
impact on whether a mainstream user can actually use the system, not impact on
funds. (Funds-loss modes are D3's domain; they recur here only where the *user
experience* of the failure is the point.)

## Methodology

- **Primary source = the spec, read as a script.** Each journey is walked
  step-by-step against the normative MUSTs of `specification.md`: §1.2 (keys /
  seed; account=address one-to-one; no sub-addresses), §1.3 (per-coin keys,
  `detect_tag` scan), §2.3.1–§2.3.3 (mint / send / receive), §3.1–§3.10
  (publisher, 6-conf finality, transaction states), §4.2 (delivery, ACK,
  self-delivery, retry/backoff), §4.3 (addressing — the `Invoice`/profile that
  **requires the recipient's `sk₀`** to issue), §4.4 (note discovery = pull
  candidates + Poseidon scan), §4.5 (recovery), §4.6 (k-replication), §5.6
  (shareable confirmation links), §6.1–§6.5 (node deployment, wallet↔node,
  portability, issuance).
- **Verified-scope reality** is taken verbatim from the Apalache package:
  `formal/CERTIFICATE.md` and `formal/property/P09_RecoveryCompleteness/notes.md`.
  Where a journey leans on a property, the document states whether that property
  is *certified* and at what grade — and, crucially, that **liveness/availability
  is NOT certified** (P9 liveness is surrogate-only; the genuine temporal form
  returns a counterexample without fairness). Every "things go wrong" branch that
  is an availability failure sits in the uncertified zone.
- **Latency anchoring.** On-chain finality is the spec's normative **6
  confirmations ≈ 60 min** (§3.9). Proving latency is anchored to the project's
  own measured proving baselines (order-of: `send` p50 ≈ 10 s, `mint` p50 ≈ 40 s,
  warm-path send a few seconds) — i.e. proving is *seconds*, the dominant wait is
  always Bitcoin's 6-conf hour.
- **Realism verdict scale per journey:** `yes` (a non-technical user can do this
  unaided) / `with caveats` (doable but needs hand-holding, defaults, or
  tolerance of a surprising wait/branch) / `no` (not realistic for a
  non-technical user as specified).
- **Three structural facts that recur** (established once, used throughout):
  1. **The spend credential is data, not a key.** A coin's value lives only in
     its off-chain `CoinProof` bundle and "cannot be derived from the seed or a
     hash" (§4.5). Seed restores keys; it does **not** restore funds. This is the
     single most counter-intuitive fact in the whole UX.
  2. **Receiving requires the recipient to have already been online with their
     wallet.** Resolving an address to a deliverable target needs a recipient-
     published `Invoice` **or** `profile` event, and **both carry `addr_sig =
     BIP-340(sk₀, …)`** (§4.3). `sk₀` is SPEND-branch, wallet-only. "Resolution
     by `address` alone … is **not** supported." So a brand-new address that has
     never run its wallet online cannot be paid.
  3. **The default mass-market user does not self-host.** The full trustless
     stack is docker + bitcoind + Nostr relay + Postgres + a public domain/TLS
     (§6.1). That is a server, not a phone. The realistic phone user therefore
     delegates `{ivk, ovk, op}` to a foreign operator and accepts a full-
     plaintext lifetime view (D3's R-D3-9). Every journey is walked for **both**
     the self-host path and the realistic foreign-operator path where they
     diverge.

## Journey 1 — First onboarding (install wallet; do I also need a node?)

**Goal.** A new user installs the wallet and reaches a state where they can
receive a payment.

### Sub-path 1a — Self-host (the "fully sovereign" path the spec defaults to)

1. User installs the wallet app; it generates a seed (BIP-39 / Passkey-PRF) and
   shows the 12/24 words. *Trust assumption:* user must store the seed — standard
   crypto onboarding, already a known drop-off point.
2. Wallet derives `address = H(Pk₀)`, `ivk/ovk/op`, `nk`, `sk₀` (§1.2).
   No wait. So far phone-friendly.
3. **The wall.** To receive trustlessly the user must stand up a node: a docker
   host running **bitcoind** + a Nostr relay + Postgres + the zkCoins node,
   reachable at a **public domain with TLS** (or a Tor onion) (§6.1). *Latency:*
   **bitcoind initial block download is hours-to-days and ~600+ GB of disk**.
   *Failure/realism:* this is **not feasible on a phone** — it is a server
   deployment. A non-technical user cannot do step 3 at all.
4. Once the node syncs, the wallet delegates `{ivk, ovk, op}` to *its own* node
   over an authenticated channel (§6.2). The user must then publish an
   `Invoice`/profile (Journey 3) so others can pay them.

> **Verdict (1a): no** for a non-technical user; **with caveats** for a
> self-hosting expert (a one-time server build, then fine). Worst branch: user
> believes "install wallet = ready," then discovers receiving requires running a
> Bitcoin full node and a public-internet service.

### Sub-path 1b — Foreign operator (the realistic mass-market path)

1. Install wallet, generate seed, derive keys (as 1a steps 1–2).
2. Wallet hands the **operational bundle `{ivk, ovk, op}`** to a foreign
   operator's node so it can detect/decrypt/serve 24/7 (§6.1 "Keys it holds";
   §1.2). *Trust assumption the user must accept (and is mostly invisible in the
   UI):* that operator now holds **lifetime, un-rotatable plaintext view** of
   every coin the account ever receives or sends (`ivk`+`ovk`+prover), and the
   keys **cannot be rotated** without abandoning the account/address entirely
   (§1.2; D3 R-D3-2/R-D3-9). The spec's own §6.2 says a wallet **MUST NOT** hand
   a *foreign* operator the bundle and should instead issue a scoped view grant —
   **but a scoped view grant cannot run a 24/7 receiving service** (it is a
   bounded *read*, not the detect+decrypt+serve role). So the realistic hosted
   product either (i) operates the user's *own* logical node on shared infra
   (still that operator's plaintext) or (ii) bends the §6.2 MUST. Either way the
   mass user trusts the operator for **privacy**, exactly as a custodial wallet
   user trusts a custodian for funds — except here the marketing says
   "trustless."
3. No bitcoind on the phone; latency is just account setup. Phone-friendly.

> **Verdict (1b): with caveats.** Mechanically easy; the caveat is that the
> "no trusted operator" promise does not hold for the privacy dimension on this
> path, and the user is not clearly told. Worst branch: user picks the only
> available operator (young network ⇒ likely a single dominant provider, D3
> R-D3-10), and that one operator silently sees everything forever.

**Headline:** the spec's flagship "self-sovereign, no trusted operator"
experience (1a) is a **server-operator** experience. The actual phone experience
(1b) reintroduces a trusted-for-privacy party. The gap between the two is the
biggest onboarding-honesty risk in the system.

## Journey 2 — Mint / create an asset

**Goal.** A creator issues a new asset (creator-bound, v1).

1. Creator enters `name`, `decimals`, initial `amount` (§2.3.1). No wait.
2. Wallet signs the mint transition with **`sk₀`** (the address-fixing key —
   mint authority is monopolised on the creator by construction, §6.5) and
   derives `asset_id` (§2.3.1 step 2). *Trust assumption for holders later:* v1
   has **no protocol supply cap** — "supply discipline is a creator's
   commitment, not a protocol guarantee" (§6.5). A holder must trust the creator
   not to over-mint; the only deterrent is that account-level over-issuance forks
   are publicly observable (§6.5). Most end users will not understand this is an
   honor-system supply.
3. Node/prover builds the witness and runs the issuance circuit (clauses a–d).
   *Latency:* proving ≈ **tens of seconds** (mint p50 ≈ 40 s). Single visible
   spinner.
4. The mint produces a self-held coin retained locally as spend credential; a
   mint **need not be anchored on-chain** (k=0 contribution). *Consequence the
   creator must accept:* an un-anchored mint coin has **no Bitcoin anchor**; a
   later viewer sees status **`mint-verified`**, explicitly distinct from
   `completed` (§5.6). Optionally the issuer can pay a publisher to anchor a
   "first appearance," at a normal on-chain cost.
5. The human-readable `name` never goes on-chain and is **never recoverable**
   from the chain (§4.5) — it lives only inside bundles. If all bundles are lost,
   the asset still exists by `asset_id` but its name is gone.

> **Verdict: with caveats.** The *mechanics* are a one-screen form + a ~40 s
> wait — fine. The caveats are conceptual and under-surfaced: (i) v1 supply is
> trust-the-creator, not enforced; (ii) un-anchored mints carry a status the
> user must understand. Worst branch: a creator (or their holders) assumes the
> protocol caps supply; it does not.

## Journey 3 — Send P2P (the central journey)

**Goal.** Alice pays Bob.

**Pre-condition that bites first (the circularity).**

1. Alice has Bob's `address`. To deliver she needs Bob's `IVPK`, `op_pubkey`,
   and **relay set** — obtainable only from a Bob-published `Invoice` **or**
   `profile`, each signed `addr_sig = BIP-340(sk₀, …)` (§4.3). *Therefore Bob
   must have been online with his wallet and published a signed
   Invoice/profile **before** Alice can pay him.* "Resolution by `address`
   alone … is **not** supported" (§4.3). *Failure branch:* Alice pastes a fresh
   address that has never published a profile → the wallet **cannot route the
   payment** and must show "recipient not reachable / ask them to come online."
   This is the **opposite** of the universal mental model "an address is enough
   to receive."
2. *Trust assumption:* Alice's wallet verifies all three Invoice checks
   (`H(pk0)==recipient`, `addr_sig`, `op` sig) — automatic, invisible. Good:
   this is what stops an attacker who scraped Bob's `Pk₀` from a public
   `BatchBundle` from substituting their own `ivpk` (§4.3).

**The send itself.**

3. Alice's wallet signs the send transition with `skᵢ`, supplies `nk` and the
   rotated `Pkᵢ₊₁` (§2.3.2). One signature; no visible wait.
4. Node/prover derives nullifiers, builds output coins (recipient coin + change
   coin), encrypts each under its `K_tx`, runs the recursive proof (§2.3.2
   steps 3–7). *Latency:* proving ≈ **a few-to-ten seconds** (send p50 ≈ 10 s;
   warm path a few seconds).
5. The `SpendRecord` is handed to a **publisher**, who batches it, builds the
   `AggregateBatchProof`, replicates the `BatchBundle` to **k=3** holders, and
   inscribes one `BatchInscription` on Bitcoin (§2.3.2, §3.4, §4.6). *Latency:*
   batching interval + Bitcoin inclusion. *Failure branch:* publisher censors or
   sits on the record → §3.4 says re-submit to another publisher after a bounded
   window; the wallet must surface "still publishing…" possibly for many minutes.
   For a phone wallet that cannot self-publish, censorship-resistance reduces to
   "some willing publisher exists" (D4 R-D4-1).
6. The recipient `CoinProof` bundle is delivered to Bob's relay set: NIP-44
   encrypted, NIP-59 gift-wrapped, blob in content-addressed store, plus a
   delivery event carrying `detect_tag/epk/blob_id/ack_nonce` (§4.2).
7. **The 6-conf wait.** Bob MUST NOT credit until the anchoring
   `BatchInscription` is `completed` = **≥ 6 confirmations ≈ 60 minutes**
   (§3.9, §3.10, §2.3.3 step 4). *This is the dominant user-visible latency of
   the entire system.* From Alice's side the payment is "sent" in seconds but
   not *confirmed-received* for ~an hour.
8. **Await ACK.** Alice's wallet **MUST** retain its copy of the bundle and
   `K_tx` and **re-publish on exponential backoff (30 s → 1 h cap)** until Bob's
   node returns a valid `op`-signed ACK echoing `ack_nonce` (§4.2). *Failure
   branch:* Bob is offline / lazy / his node never ACKs → Alice's wallet carries
   an **unbounded retained-copy + retry obligation** (D4 R-D4-5). The user sees a
   payment stuck in "delivering…" indefinitely with no defined give-up state.

> **Verdict: with caveats**, trending to **no** for the naive case. The
> happy-path UX (sign → ~10 s proof → ~1 h to confirmed) is comparable to an
> on-chain Bitcoin payment and is acceptable. The two genuine blockers are
> (a) **the recipient-must-have-published-first circularity** (step 1), which
> breaks "send to any address," and (b) the **~60-min confirm wait**. Worst
> branch: paying a never-online address simply cannot be done, and the wallet
> can only say "tell them to open their app."

## Journey 4 — Receive (come online after being offline)

**Goal.** Bob, who was offline, opens his wallet and finds Alice's payment.

1. Bob's node (holding `ivk`) derives `dk = HKDF(DetectKey, ivk)` (§4.4 step 1).
2. **Pull candidate delivery events** from the relay set. The relay **cannot**
   pre-filter for Bob (it lacks `dk`), so Bob pulls the **full candidate set**
   (§4.4 step 2, §4.7). *Cost:* one cheap Poseidon hash per candidate, but the
   *bandwidth* is the whole candidate stream. *Failure/realism:* on a self-
   hosted always-on node this is fine; for a **thin/mobile** client that does its
   own scanning this is a real bandwidth/battery cost that grows with network
   traffic (mitigated only by the OPTIONAL fuzzy-message-detection pre-filter,
   §4.4 — not in base). In practice the foreign operator does the scan, which is
   exactly why the mass user delegates `ivk` (Journey 1b) — re-confirming the
   privacy trade.
3. For each `detect_tag` match: derive `K_tx`, fetch the blob, trial-decrypt
   (§4.4 step 3). *Failure branch:* blob unreachable (no replica answers) →
   delivery event seen but bundle missing; the coin shows as "incoming, not yet
   retrievable," an availability stall, **not** certified safe-against (P9
   liveness is surrogate-only — see `notes.md`).
4. **Re-verify the full recursive proof** client-side (§2.3.3 step 2, MUST pass)
   + inclusion in `ocr` (step 3). *Latency:* constant-time verify, sub-second.
5. **Anchoring + finality:** confirm the coin's `ocr` is bound by a `SpendRecord`
   whose `BatchInscription` is `completed` (≥6 conf) (§2.3.3 step 4). If still
   `pending` (under 6 conf), Bob sees "incoming — confirming (≈X min left)."
6. **Nullifier non-membership** against the live accumulator at `NAV(tip)`
   (§2.3.3 step 5) — Path A (run own accumulator) or Path B (light-client SMT
   path). For a phone, Path B asks the operator's node and self-checks against
   the on-chain root.
7. On all checks passing: credit; the bundle becomes Bob's spend credential;
   return the ACK (§2.3.3, §4.2).

> **Verdict: with caveats.** For a delegated (operator-served) user the
> experience is "open app → balance appears, with a confirming timer for recent
> payments" — good. The caveats: (a) self-scanning thin clients pay a
> non-trivial bandwidth cost (R-D6-7); (b) the only honest framing is that the
> always-on detect/decrypt that makes "money just appears" work is what the
> operator does with the user's `ivk`. Worst branch: blob DA stall — money was
> sent, proof exists on-chain, but the value-bearing bundle is unreachable, so
> the coin cannot be credited (uncertified liveness zone).

## Journey 5 — Multi-device setup (one seed, two devices)

**Goal.** Bob uses the same account on phone and laptop; he spends on the phone,
then opens the laptop.

1. Both devices derive the same keys from the seed (§1.2). No per-device state
   (§6.3). So far seamless.
2. **The hard precondition:** the chain reveals *nothing* per-account — not the
   new `ash`, not the balance, not the proof the next spend must extend (§4.2
   self-delivery note). A second device learns of a spend made elsewhere **only**
   by discovering the **self-addressed change/state bundle** on a **shared
   relay** (§4.2, §4.4). Therefore devices that must stay in sync **MUST share at
   least one advertised relay** (§4.2, §6.3). *Trust/assumption the user must
   accept (and almost certainly won't configure consciously):* there must be a
   common relay both devices reach, and the self-delivered bundle must be present
   and replicated there.
3. **Spend on phone → open laptop (happy path):** phone's node self-delivers the
   change/state bundle to the shared relay set; laptop pulls candidates,
   `detect_tag`-matches its own self-bundle, fetches it, verifies, and updates to
   the new `send_counter`/balance. Works — *if* the shared relay held the bundle.
4. **Failure branch (the dangerous one):** laptop did **not** see the
   self-delivered bundle (different relay set, bundle dropped, effective k=1 on a
   self-hoster — D3 R-D3-1). The laptop can detect from Bitcoin that an
   accumulator transition occurred but **cannot reconstruct the spendable state**
   and **must fall back to emergency reconstruction** (§4.2, §4.5). *What the user
   experiences:* the laptop shows a **stale balance / stale `send_counter`**.
5. **The equivocation trap.** If the user, seeing a stale laptop, *signs a new
   spend from the laptop against the stale state*, they produce **two parallel
   transitions at the same `send_counter`** — an **account-level fork**. The spec
   says a wallet detecting this **MUST NOT sign further until the user resolves
   it**, and "the protocol does not automatically pick a fork-winner; the choice
   is the holder's" (§6.3). *What a non-technical user experiences:* a wallet that
   refuses to send and asks them to "resolve a fork" — an utterly opaque error,
   and the §6.5 note warns this same signature pattern is what over-issuance /
   custody-breach detection keys on, so the wallet may even imply something
   alarming.

> **Verdict: no** for a non-technical user as specified. Naive multi-device "use
> the same wallet on two devices" — the universal expectation set by every
> custodial and most non-custodial wallets — is **not** safe here without a
> shared-relay invariant the user cannot be expected to manage, and the failure
> mode is a self-inflicted fork that hard-stops spending. Worst branch: stale
> second device → user signs → permanent account fork requiring manual,
> unexplained resolution.

## Journey 6 — Key loss + recovery (seed survives, devices/node gone)

**Goal.** Bob lost his phone and his node; he has only his seed.

1. **Re-derive keys** from seed: `ivk/dk/ovk/op/nk/sk` (§4.5 step 1). Restores
   identity, decryption, detection tags. No wait.
2. **Rebuild the accumulator from Bitcoin + bundles:** scan all
   `BatchInscription`s, fetch each `BatchBundle`, verify each
   `AggregateBatchProof`, apply root transitions (§4.5 step 2). *Latency:* a full
   historical scan — minutes-to-hours depending on chain depth and bundle fetch.
   *Conditional on bundle DA:* if every replica of a past `BatchBundle` is lost,
   the operator can verify root continuity but cannot reconstruct that batch's
   member set (§4.5 step 2).
3. **Pull candidate bundles** from the network's capability-gated pull endpoints,
   **by proving ownership (sign a challenge) or by presenting the `detect_tag`
   set** (§4.5 step 3). The network is "an untrusted blob cache." *Privacy cost
   the user pays — and is not warned about:* recovery **forces identification to
   operators** — pulling by ownership reveals the requester's identity; pulling
   by `detect_tag` reveals the tag set / history cardinality to the serving node
   (§4.7 "Recovery disclosure"; D3 R-D3-6). There is **no anonymous-retrieval
   mode**.
4. **Verify each returned bundle against Bitcoin** (§4.5 step 4). *This is the
   certified-safe step:* P9's safety half is **verified unbounded** — no
   forged/unverifiable bundle ever enters `recovered`, the verify gate is
   machine-checked load-bearing (`P09 notes.md`, negative control fires). So a
   malicious operator returning forgeries cannot poison recovery.
5. **Rebuild `AccountState`/balances** from accepted incoming + outgoing coins
   (§4.5 step 5).
6. **The dead-end.** Coin **values** "exist only in the `CoinProof` bundles and
   cannot be derived from the seed or a hash" (§4.5). If a bundle is gone from
   all replicas, **that value is unrecoverable** — the seed cannot bring it back.
   *This is the certified-uncertified boundary:* false-accept is impossible
   (P9 HIGH), but false-reject-by-unavailability is **liveness, MEDIUM, NOT in
   the certificate** — the genuine temporal liveness "every own bundle is
   eventually recovered" returns a **counterexample without fairness** (`P09
   notes.md`: "without fairness the untrusted network can withhold forever").

> **Verdict: with caveats**, and the caveats are severe. *Identity/keys* recover
> cleanly and the result is trustless (certified). *Funds* recover **only if the
> bundles are still available** — which the formal layer explicitly does **not**
> guarantee, and which on a self-hoster can be effectively k=1 (D3 R-D3-1). The
> user's mental model — "I have my seed, so my money is safe" — is **wrong** here
> and the wallet does not say so. Worst branch: seed restored, balance comes back
> as a fraction (or zero) because change/value bundles were lost, with no error
> that explains *why* the number is lower than the user remembers (D3 R-D3-13).

## Journey 7 — Operator switch (move to a new node)

**Goal.** Bob, unhappy with operator X, moves to operator Y.

1. Switch is "by configuration alone, with no migration step" — no node can lock
   a wallet in (§6.3). The wallet points at Y, fetches state, verifies against
   Bitcoin. *Mechanically:* genuinely easy; this is a real strength.
2. **What Bob must hand Y:** to get the same 24/7 receiving service, Y needs the
   operational bundle `{ivk, ovk, op}` (or Bob runs his own node). So switching
   operators = **handing a second operator the same lifetime plaintext keys**.
3. **The old operator does not lose its view.** `ivk/ovk/op` are fixed hardened
   seed derivations that **do not rotate** (§1.2; D3 R-D3-2). Operator X **keeps
   lifetime read access to all future activity** of the account even after the
   switch, because the keys it was given still decrypt everything. The only way
   to evict X is to **abandon the account/address entirely** and tell every
   counterparty the new address. *What the user experiences:* "switched
   operators" feels like leaving a provider, but privacy-wise the old provider is
   still reading everything forever.
4. **Pending ACKs / grants / revocations.** In-flight deliveries Bob hadn't
   ACKed, and any view-grant **revocations**, are per-node runtime state, **not
   seed-restored** — a node switch can silently **un-revoke** previously revoked
   grants (D3 R-D3-7). The user is not told.
5. **Republish profile.** After switching relays/`op` advertisement, Bob must
   re-publish his `Invoice`/profile so senders resolve to Y's relays (§4.3) —
   another "must be online with wallet to be reachable" step (the Journey 3
   circularity, again).

> **Verdict: with caveats.** The "no lock-in, switch by config" property is real
> and good for the *correctness/availability* dimension. But the **privacy**
> story of a switch is the opposite of what users expect: you cannot actually
> revoke the old operator's view short of a new identity, and revocations can
> silently reset. Worst branch: user "leaves" a creepy operator believing they
> cut it off; it retains full plaintext view for the life of the account.

## Journey 8 — Backup / restore (what is "backup" beyond the seed?)

**Goal.** Bob wants to be sure he can recover. He writes down his seed.

1. The spec is explicit: "the seed is the **only required backup**"
   (§4.5, §1.2). Every wallet UI will say this. It is **true for keys/identity**
   and **false for funds.**
2. **The real spend credential is the bundle store**, not the seed: a coin's
   value lives only in its `CoinProof`/change bundle and **cannot be derived from
   the seed** (§4.5; Glossary *Bundle* = "simultaneously the recipient's receipt
   and its spend credential"). The genuinely durable backup is therefore the
   **node's data store** (the "Primary — node operator's own backup" path of
   §4.5), with the network's k=3 replication as the fallback.
3. **Is the user told?** The normative text says the seed is the only *required*
   backup and that the node *SHOULD* keep its own durable backup — but the
   user-facing consequence (**seed alone ≠ funds**) is nowhere mandated as a
   wallet disclosure. A non-technical user who backs up only the seed and lets a
   single operator hold the only bundle copy (effective k=1, D3 R-D3-1) is one
   disk failure away from losing live balance **despite having "done backups
   right."**
4. **Restore** then proceeds as Journey 6 (operator backup if available, else
   network reconstruction with its DA dependence and privacy cost).

> **Verdict: no** as currently communicated, for a non-technical user. The
> universal, hard-won crypto lesson "your seed is your money — back it up" is
> **actively misleading** in zkCoins, and the spec does not require the wallet to
> correct it. Worst branch: user confidently holds only the seed, the bundle
> store is lost, and funds are gone with the user believing backups were correct.

## Journey 9 (optional) — Offline transaction use case

**Goal.** Can Alice pay Bob with no connectivity (the "tap-to-pay offline" idea)?

1. A send requires: handing the `SpendRecord` to a **publisher** who broadcasts a
   Bitcoin inscription (needs connectivity), and delivering the `CoinProof`
   bundle to Bob's **relay** (needs connectivity), and Bob crediting only after
   **6 confirmations** (needs Bitcoin) (§2.3.2, §3.x, §4.2).
2. Every settlement-bearing and value-bearing step is online. There is **no
   offline-capable instrument** in the protocol (no bearer note that finalizes
   later à la a Lightning/ecash voucher; the bundle is bearer *data* but it still
   must be DA-replicated and the spend must be accumulator-anchored to be safe to
   accept). At best, Alice could *prepare* a signed bundle offline and *transmit*
   it later — but Bob cannot **safely credit** it until it is on-chain-anchored
   and accumulator-checked, so it is not an offline *payment*, only a deferred
   online one.

> **Verdict: no** — "offline payment" is **not a concept in this protocol**.
> This is not a defect so much as a scope fact, but it should be stated, because
> "private cash on Bitcoin" framing invites the offline-cash expectation. Worst
> branch: a user treats a handed-over bundle as settled cash and is double-spent
> (the original spender can race a different spend before anchoring; only the
> accumulator check at credit time protects Bob, and that requires him online).

## Cross-journey UX risks

These are the recurring, structural UX problems that no single journey owns.

- **C1 — The "receive needs prior online publish" circularity.** You cannot pay
  an address that has never run its wallet online to publish a signed
  `Invoice`/profile (§4.3; Journeys 1, 3, 7). This breaks the single most
  universal payment mental model ("an address is enough to receive"). It also
  means onboarding has a chicken-and-egg: to *be paid* you must first be *set up
  and online*.

- **C2 — Seed-is-not-enough-for-funds.** The seed restores keys, never the
  value-bearing bundles (§4.5; Journeys 6, 8). This contradicts the deepest
  ingrained crypto lesson and is **not** required to be disclosed to the user.
  Highest-impact mismatch between mental model and reality.

- **C3 — The ~60-minute confirm wait on every received payment.** 6-conf
  finality (§3.9) is the dominant latency (Journeys 3, 4). Acceptable for
  store-of-value transfers, poor for point-of-sale; proving is *seconds*, so the
  hour is pure Bitcoin finality and cannot be engineered away without an
  out-of-band lower-confirmation acceptance policy (which the user must then
  understand the risk of).

- **C4 — detect_tag scan bandwidth on mobile.** Detection is not server-
  filterable; a self-scanning thin client pulls the full candidate set (§4.4,
  §4.7). This is the technical reason the mass user delegates `ivk` — which is
  the privacy trade of C6. Fuzzy message detection is OPTIONAL, not base.

- **C5 — Running bitcoind is the price of the "trustless" path.** The sovereign
  experience is a server (docker + bitcoind IBD + relay + Postgres + public TLS,
  §6.1; Journey 1a). It is not a phone experience. The honest mass-market path is
  foreign-operator delegation.

- **C6 — "Trustless" overclaim on the default path.** The realistic user hands
  a foreign operator `{ivk, ovk, op}` and gets a **lifetime, un-rotatable,
  full-plaintext** privacy exposure (Journeys 1b, 4, 7) that the "no trusted
  operator" framing actively hides. Switching operators does not revoke it
  (Journey 7). This is the same gap D3 names (R-D3-9, R-D3-2) seen from the UX
  side.

- **C7 — Multi-device equivocation hard-stop.** Naive "same wallet, two devices"
  can desync (no shared relay / bundle DA) and a spend from a stale device
  produces an account fork that **halts spending** with an opaque "resolve a
  fork" demand (§6.3; Journey 5). The very behavior the spec uses to *detect
  custody breach* is what a confused two-device user trips by accident.

- **C8 — No defined give-up state for the sender's ACK/retry obligation.** The
  sender retains and retries indefinitely until ACK (§4.2; Journey 3), so a
  lazy/offline recipient leaves a payment "delivering…" forever in the sender's
  UI (D4 R-D4-5).

- **C9 — Recovery forces de-anonymisation to operators.** No anonymous-retrieval
  mode; recovery reveals identity or tag-set/history cardinality to the serving
  node (§4.7; Journey 6; D3 R-D3-6).

- **C10 — Status vocabulary the user must learn.** `pending` (confs) vs
  `pending` (DA) vs `completed` vs `failed` vs `mint-verified` (§3.10, §5.6).
  Five states, two of them confusingly both "pending," and `mint-verified`
  means "no on-chain anchor — trust the issuer." Surfacing these honestly
  without alarming or confusing users is a real design problem.

## Findings

Severity = UX-adoption impact (Critical = breaks a journey for the mainstream
user / silent surprise that loses funds or trust; High = a journey is unworkable
or actively misleading for a non-technical user; Medium = needs hand-holding /
defaults / surprising-but-survivable wait or branch; Low = edge case or
documentation polish). Likelihood = for the realistic young-network, mostly-
foreign-operator deployment.

## Recommendations

| ID | Recommendation | Addresses |
|---|---|---|
| **RC-D6-1** | **Mandate a wallet disclosure that the seed alone does not restore funds**, and make bundle-store backup (or a verified ≥k independent replica count) a first-class, surfaced part of the backup flow — not buried in "your node SHOULD back up." Show the user a "funds-recoverability" indicator, not just "seed saved." | R-D6-1, R-D6-8 |
| **RC-D6-2** | **Fix the receive circularity in the UX**: auto-publish a signed profile at account creation (one-time online step), and have the wallet say plainly "you must open this app once before others can pay you." Consider a lightweight address-resolution fallback so a never-online address gives a clear, actionable error rather than a dead end. | R-D6-2 |
| **RC-D6-3** | **Stop framing the foreign-operator path as "trustless."** Add an honest privacy disclosure at operator selection: "this operator can see all your amounts, assets, and counterparties for the life of this account, and you cannot revoke this without a new account." Reconcile the §6.2 MUST-not-hand-foreign-bundle clause with how a hosted 24/7 service actually works. | R-D6-3, R-D6-4, R-D6-9 |
| **RC-D6-4** | **Make multi-device a designed flow, not an accident**: enforce a shared-relay invariant when a second device is added, block signing from a device that cannot confirm it holds the latest `send_counter`, and replace "resolve a fork" with a guided, plain-language recovery. Treat accidental same-counter signing distinctly from custody-breach detection. | R-D6-5 |
| **RC-D6-5** | **Set realistic latency expectations and offer a documented low-conf policy** for low-value/POS use, with the risk shown; never present the 6-conf hour as instant. | R-D6-6, R-D6-13 |
| **RC-D6-6** | **Ship fuzzy-message-detection (or operator-side scan) as the default** so thin clients are not pushed into full-candidate self-scan or forced `ivk` delegation purely for bandwidth. | R-D6-7 |
| **RC-D6-7** | **Add an anonymous/oblivious recovery-retrieval option** so seed-only recovery does not de-anonymise the user to operators. | R-D6-11 |
| **RC-D6-8** | **Bound the sender's ACK obligation**: define a give-up/timeout state and a "delivered-unacknowledged" UI, and make ACK automatic in the reference node. | R-D6-10 |
| **RC-D6-9** | **Design the status vocabulary for humans**: distinguish the two `pending` causes in copy, and explain `mint-verified` as "issuer-attested, not Bitcoin-anchored." | R-D6-12, R-D6-14 |
| **RC-D6-10** | **State the supply-trust model at the point of asset creation and asset acceptance** ("v1 supply is the creator's promise, not protocol-enforced"). | R-D6-14 |

## Verdict

The end-to-end UX is **realistic only for a self-hosting expert** in its
flagship "fully sovereign" form, and **realistic with significant caveats for a
crypto-native user** on the foreign-operator path — provided that user accepts a
custodial-grade *privacy* trust they are told is "trustless," tolerates a
~60-minute confirm wait, and never naively runs two devices. It is **not yet
realistic for a mainstream, non-technical user**: three universal mental models
are violated and not corrected by the spec — *an address is enough to receive*
(C1/R-D6-2), *my seed is my money* (C2/R-D6-1/R-D6-8), and *the same wallet works
on my phone and laptop* (C7/R-D6-5) — and the default privacy posture is the
opposite of the marketing. The cryptography is sound and largely certified for
*safety*; the **adoption risk lives entirely in UX honesty and liveness**, which
are exactly the dimensions the formal layer does not (and says it does not)
cover.
