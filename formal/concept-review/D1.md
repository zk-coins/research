# D1 · Property Completeness — Are P1–P10 the right and complete set?

**Dimension:** D1, concept viability. **Question:** Is the verified P1–P10 set the *right* and
*complete* set of guarantees for what zkCoins promises to its users, and which fundamental
conceptual guarantees does the protocol need that were never stated and never checked?

This is **not** a crypto-correctness review. The cryptographic soundness of each stated property
is machine-verified (Apalache) and manually argued (Pass-3) elsewhere, conditional on the named
axioms and meta-assumptions. D1 asks the orthogonal question: *of the things a user must be able
to rely on for the concept to be sound, which ones are simply absent from the property set?*

## Methodology

**Sources read.**

- The specification (post-Variant-2 redesign): §3 on-chain layer (publisher, `BatchInscription`,
  `BatchBundle`, accumulator, fees, finality, states), §4 transport/recovery/data-availability,
  §5 access & disclosure, §6 architecture (wallet↔node, portability/multi-node, issuance v1,
  threat model, requirements traceability), and the "ten requirements".
- The verification artefacts: the certificate of completion, the per-property status table, and
  the Pass-3 manual audit §4 (the P1–P10 game statements), §6 (findings F16/F17 and carry-forward),
  §7 (confidence summary) and §8 (residual inventory R1–R4).
- Project notes: the threat model (sender-equivocation S2, SSS-bypass S3, replay S4, fee
  front-running S5, force-exit spam S6/S7, selective-withhold S8, economic attacks), the L2
  protocol-design note, and the SSS trust-model note.

**How judged.** For each candidate gap I asked four questions:

1. Is the guarantee *load-bearing* for a normal user's expectation of the system (custody, payment,
   recovery, privacy, supply, governance)?
2. Is it already delivered — in substance, not just in name — by some Pᵢ or by an explicit design
   clause the spec is honest about?
3. If not delivered: is the absence *fundamental* (no parameter choice or operational discipline
   closes it) or merely *operational* (closeable by deployment hygiene)?
4. What is the concrete user harm if it is violated, the severity if left unaddressed, and the
   likelihood under realistic deployment?

Accepted gaps get an ID `P11+`, a one-sentence game-style statement, a fundamentality judgement,
a *verifiable formally / inherently operational* tag, and severity × likelihood. Rejected
candidates get one honest sentence each. Findings carry IDs `R-D1-n`.

**Honesty mandate.** Negative findings are stated plainly. Where a gap is fundamental I say so. I do
not credit the protocol for guarantees it only *names*; I credit it only for guarantees it *delivers*.

## The P1–P10 lens — what the verified set actually covers

Read against the user's needs, the verified set is **almost entirely a safety set, almost entirely
about a single honest party in isolation, and conditional in three layered ways**. This shape is
the key to what is missing.

- **It is a safety set, not a liveness set.** P1 (no-forgery), P2 (no-double-spend), P3 (balance
  conservation), P4 (zero-knowledge), P5 (on-chain unlinkability), P6 (client-side validation), P7
  (issuance authenticity), P8 (transport confidentiality+auth), P10 (capability discipline) are all
  "*nothing bad can happen*" statements. The only property that touches "*something good eventually
  happens*" is P9 (recovery completeness) — and its liveness half is **not** verified: the
  certificate records it as an "enabledness surrogate" because Apalache 0.58.0 has no fairness
  support and the genuine `WF ⇒ ◇□` form throws `NotImplementedError`. So the set proves the
  protocol cannot be made to *lie* or to *steal*; it proves almost nothing about the protocol being
  able to *make progress* for the user. Every "can a thing the user needs actually happen?" question
  is outside the verified frame.

- **It is single-party-in-isolation, not multi-party-under-contention.** Each game pits one
  adversary against one honest victim's local checks. There is no property about two honest parties
  competing for the same on-chain slot, about ordering fairness across a batch, about one user's
  batch being griefed stale by another, or about a user's own two devices disagreeing. The spec
  *describes* these situations (§3.4 sequential commitment, §3.7 reorg replay, §6.3 fork-halt) but
  no Pᵢ *guarantees* an outcome in any of them.

- **It is conditional in three stacked layers**, all honestly recorded: (i) cryptographic axioms
  A1–A17 (consumed, not proven; R1 Poseidon margin ~95 bits is the live one); (ii) meta-assumptions
  M1–M4 (tool soundness, translation fidelity, adversary-model completeness, property-statement
  correctness); (iii) per-property sub-scopes — P1 signature-level bounded, P2 continuity bounded,
  P4/P5 indistinguishability = axiom A2 (the hyperproperty half is *assumed*, not proven), P5
  network-layer out of scope, P9 liveness surrogate, P10 spend-escalation structural. The
  composition is verified; several *leaves* of the composition are assumptions wearing a proof's
  clothing, and the certificate says so.

**The decisive observation for D1.** P1–P10 answer "*is each thing the spec claims, true?*" with a
defensible YES. They do **not** answer "*are the things the spec claims the right and complete set
of things a private Bitcoin-anchored money needs to claim?*" The adversary-model-completeness
meta-assumption **M3 is exactly the door through which every D1 gap below walks**: a property that
was never stated cannot be mis-stated, so M4 (property-statement correctness) never fires on it, and
M3 (did we model the right adversary/goal at all?) silently absorbs it. The verification is a
faithful proof of an incomplete specification of *goals*.

## Missing properties (P11+)

### P11 · Censorship-resistance of spend inclusion (`R-D1-1`)

**Statement (game).** An adversary controlling some-but-not-all publishers and relays cannot
prevent an honest, fee-paying spender's `SpendRecord` from eventually reaching a `completed`
`BatchInscription`, given the spender retains the ability to self-publish.

**Rationale / why fundamental.** Every Pᵢ is about what happens to a spend *once it is anchored*;
none guarantees a spend *gets* anchored. §3.4 makes publishing permissionless and lets the censored
spender "submit to a different publisher" or self-publish — but that is a **cost shift, not a
guarantee**. Self-publishing requires the spender to (a) build or commission a recursive
`AggregateBatchProof` (~100 KB, non-trivial proving cost — §3.4 explicitly says a publisher is
"computationally heavier than a plain broadcaster"), (b) hold spendable BTC at a UTXO to pay the
inscription fee, which **directly punctures the very on-chain privacy P5 protects** (the broadcaster-
paid model of §3.8 exists precisely because self-funding leaks a UTXO), and (c) win the
sequential-commitment race against better-resourced publishers. So the protocol's answer to
censorship is "become a publisher yourself" — viable for a well-resourced, BTC-holding, technically
capable user, and a hard wall for a thin-wallet mobile user with no on-chain BTC. If all reachable
publishers refuse a user (price discrimination, deny-listing, or simple unprofitability of small
records), a user who cannot self-publish **cannot transact at all** while their funds remain
provably safe — money that is safe but unspendable. This is the single most important gap in the set.

**Verifiable formally or operational.** **Inherently operational** at the strong form ("a spend
*will* be included"), because it depends on at-least-one-honest-and-willing publisher existing and
being reachable — an economic/network liveness assumption Apalache cannot certify (same class as P9
liveness). A *weaker* formal property is checkable and should be stated: "self-publication is always
*enabled* for a spender holding the spend key and a funding source" (an enabledness invariant on the
publisher role, analogous to the P9 surrogate).

**Severity / likelihood.** **HIGH** severity (it is the difference between "censorship-resistant
money" and "money you can hold but a cartel of publishers can freeze from spending"), **MEDIUM**
likelihood (publisher economics for small records are genuinely thin; a few well-capitalised
publishers serving most volume is the natural market structure, and a thin client has no cheap
fallback). Mitigation sketch: a normative *self-publication enabledness* property + a costed,
documented "emergency self-publish without an existing BTC UTXO" path (e.g. a minimal proving
service the wallet can invoke) so the fallback is real for the median user, not only the whale.

### P12 · Accumulator data-availability as a safety/verifiability property (`R-D1-2`)

**Statement (game).** An adversary cannot drive the global nullifier accumulator into a state whose
correctness *no honest party can verify*, i.e. for every admitted `BatchInscription` at least one
honest holder of its `BatchBundle` remains reachable so that any verifier can validate the
`prev_root → new_root` transition at any time.

**Rationale / why fundamental.** Post-Variant-2, the on-chain object is *only* roots + a locator;
the nullifiers and the `AggregateBatchProof` live off-chain in the `BatchBundle`. §3.6 and §4.6 are
explicit and honest: a verifier who cannot fetch a bundle **cannot admit that root transition** and
leaves the inscription `pending`-due-to-DA forever; §4.6 names the worst case outright — "universal
long-term unavailability of a `BatchBundle` would leave its accumulator transition forever
unconfirmable — a soft fork of the network into 'nodes that admitted it before DA loss' and 'nodes
that never could.'" That is a **chain-liveness-and-consistency dependency for the entire network on
off-chain data**, and it is exactly the kind of thing that should be a named, first-class property
of the accumulator. The §4.6 "Safety invariant" correctly proves DA loss can never cause *theft*;
it does **not** address that DA loss can split the network's view of *which root is canonical and
verifiable* — a safety-of-consensus concern distinct from custody safety. The spec mitigates with
`k=3` + monotone scanner retention, which makes the bad outcome *unlikely*, but unlikely is a
parameter argument, not a guarantee, and "every honest scanner that ever saw it" can still trend to
zero for an old, rarely-fetched batch. The accumulator is the protocol's only consensus object;
"its progress is verifiable by anyone at any time" deserves to be a property, and it is not one.

**Verifiable formally or operational.** **Hybrid.** The structural half — "admission requires the
bundle to verify; an unverifiable transition is *never* silently admitted" — is already a verified
consequence of the §3.6 admission rules (this part is genuinely covered). The *availability* half —
"a verifiable bundle remains reachable" — is **inherently operational** (a replication/economics
assumption), the same class as P9 liveness and P11. The gap is that the operational half is not
elevated to a stated property with an explicit failure-mode classification.

**Severity / likelihood.** **HIGH** severity (a permanently unavailable admitted bundle is a
network-wide consistency fork, not a one-user problem — it is the closest thing zkCoins has to a
chain-halt), **LOW–MEDIUM** likelihood (the `k=3` + indefinite scanner-retention regime is strong;
the residual is old batches, adversarial DA targeting of a specific batch, and the absence of any
*incentive* for an independent party to keep serving a `BatchBundle` it has no custody stake in —
note the asymmetry §4.6 itself flags: a `CoinProof` bundle has a natural long-term holder, a
`BatchBundle` does not). Mitigation sketch: state the property; require a minimum independently-
incentivised archival role (or an erasure-coded DA scheme) for `BatchBundle`s; specify verifier
behaviour on a *persistently* (not transiently) unavailable bundle so two honest nodes cannot
permanently disagree on the canonical tip.

### P13 · Multi-device / single-seed consistency (`R-D1-3`)

**Statement (game).** Two honest devices driven from the same seed cannot be led — by relay
withholding or by their own race — into crediting or spending from divergent account states without
the divergence being *detected and safely halted* before any unsafe spend.

**Rationale / why fundamental.** This is a guarantee about the user against *themselves and the
network*, not against an adversary, and it is the one most likely to bite a normal user. The
account model is a single linear lineage keyed by `send_counter`; §6.3 (F12 resolution) says a
wallet detecting two verifying answers with the same `send_counter` but different
`new_account_state_hash` **MUST halt and let the user resolve**. That is *detection*, not
*prevention*: the spec is candid that "sole legitimate control of `sk₀`/`skᵢ` never produces
equivocation," so a fork means operator error (same seed on two devices over stale state) or a
SPEND-branch breach. The viability question D1 must answer: **is "wallet halts, user resolves" a
viable guarantee for a consumer product?** For a single power user, yes. For the multi-device
household / shared-custody / flaky-sync reality the spec *explicitly supports* via self-delivery
(§4.2), the honest assessment is that **silent under-counting is the more common failure than a
clean fork**: device B that never received device A's self-delivered change bundle does not see a
*fork*, it sees a *stale-but-internally-consistent* state (§4.2: "can detect that an accumulator
transition occurred but cannot reconstruct the spendable state"), and if device B then spends
against that stale state it manufactures the very same-counter fork *after the fact* — at which
point the only protection is that its spend will lose the sequential-commitment race or be caught at
detection. No property bounds the window or guarantees the loser's funds are recoverable rather than
merely "safe but stuck."

**Verifiable formally or operational.** **Partly formal.** "No two distinct admitted transitions
share a `send_counter` in a single honest lineage" is a checkable safety invariant on the spend
flow (and is close to what P2 + the §6.3 rule already imply). "Divergence is always *detected*
before an unsafe credit" is checkable. "The user can always *recover* from a detected fork without
loss" is **operational** and currently unspecified.

**Severity / likelihood.** **MEDIUM** severity (no theft, no double-credit — the safety floor
holds; the harm is a wedged wallet and a confused user, plus a possible temporarily-stuck change
coin), **MEDIUM–HIGH** likelihood (multi-device on one seed is a first-class supported scenario and
relay-sync gaps are ordinary, not adversarial). Mitigation sketch: state the detection guarantee as
a property; specify a deterministic, loss-free fork-resolution procedure (not just "user resolves");
and add a normative pre-spend freshness gate stronger than "fetch latest state" so a stale device
refuses to spend rather than racing.

### P14 · Receiver non-repudiation / payer's proof-of-payment (`R-D1-4`)

**Statement (game).** A payer who has completed a payment can produce evidence that a third party
(or the recipient) cannot credibly deny establishes the payment was made and delivered to the
recipient.

**Rationale / why fundamental.** P8 covers transport *confidentiality + authentication* and the ACK
exists for *delivery reliability* (sender knows when to stop retrying); §5.6 shareable-confirmation
links let a payer hand over a `zkview` that *proves the payment exists and is anchored*. But two
real payer needs are unmet by any property: (1) **the payer cannot prove the recipient actually
received/credited it** — the §4.2 ACK is `op`-signed and now `ack_nonce`-bound (F17 closed), which
is good, but the ACK is a *private* artefact for the sender's retry logic, not specified as a
*portable, third-party-verifiable* receipt; and (2) the threat model's **S8 (selective withhold)**
is the dual: a sender can anchor a spend on-chain (consuming the coin, "looking paid") and never
deliver the `CoinProof` bundle, leaving funds "functionally locked — nobody can spend them," and
**S2 (sender equivocation)** notes "without a sender bond, no economic penalty for sender
equivocation; reputation is the only deterrent." So neither side can hold the other to account: the
payer cannot prove receipt, and the payee cannot prove non-receipt except by negative evidence. For
a payments system whose entire pitch is "*here is verifiable proof I sent it*" (§5.6 verbatim), the
absence of a non-repudiation property is a conceptual hole, not a feature gap.

**Verifiable formally or operational.** **Mostly operational / protocol-design**, with a checkable
core: "a valid, `ack_nonce`-bound ACK is unforgeable and uniquely binds (this coin, this delivery,
this recipient `op`)" is formally checkable and largely follows from P8 — but elevating the ACK to a
*portable receipt* and defining what "proof of payment" means against a recipient who refuses to ACK
is a design choice the spec has not made.

**Severity / likelihood.** **MEDIUM** severity (commercial/regulatory usability and dispute
resolution; not a custody or privacy break), **MEDIUM** likelihood (every real payment relationship
eventually hits a "did you pay me?" / "I never got it" dispute). Mitigation sketch: define a
portable, third-party-verifiable receipt derived from the ACK + the on-chain anchor; document
explicitly that proof-of-*receipt* is impossible without recipient cooperation (an inherent property
of any store-and-forward channel) so the limit is stated rather than implied away by the §5.6
marketing line.

### P15 · Asset-issuer continuity / supply observability (`R-D1-5`)

**Statement (game).** For any asset, holders can (i) continue to use the asset even if the creator
disappears, and (ii) observe enough on-chain/bundle evidence to detect creator over-issuance
against any off-chain supply commitment.

**Rationale / why fundamental.** v1 issuance (§6.5) binds mint authority irrevocably to the
creator's `sk₀`. Two distinct fundamental risks live here, only one of which the spec addresses.
**(i) Continuity:** P7 guarantees only the *creator* can mint; it says nothing about what happens
when the creator's key is lost or the creator goes hostile. *Transfer* of existing holdings does not
need the creator (good), so holdings are not bricked — but the asset's supply is frozen and no new
issuance, redemption, or recovery is possible; there is no protocol notion of issuer succession,
multi-sig issuance (deferred to v2), or migration. For a single-user token this is fine; for any
asset meant to be a real instrument it is a single-point-of-failure with no stated bound. **(ii)
Observability:** the spec *does* handle this and handles it honestly — §3.3-balance audit + §6.5
state that creator equivocation/over-issuance is "publicly observable on Bitcoin" because the
rotating `Pkᵢ` appears in two `SpendRecord`s, and P3 is explicitly framed as "supply *discipline*,
not supply *conservation*." So the observability half is a *documented design choice*, not a gap —
**but it is not stated as a property** (P3 is conservation-relative-to-issued, which silently
assumes honest issuance accounting). The gap worth an ID is **continuity** plus **elevating
supply-observability to a checkable property** rather than prose.

**Verifiable formally or operational.** Continuity is **operational/design** (it requires a v2
issuance schema feature that does not exist — succession/multi-sig). Supply-observability is
**formally checkable** as a property ("any two mints under the same lineage are linkable by an
honest holder with view access / are detectable on-chain by their root continuity").

**Severity / likelihood.** **MEDIUM** severity for continuity (asset-specific, not protocol-wide;
v1 is explicitly "minimal"), **LOW–MEDIUM** likelihood (creator key loss is real but the spec is
upfront that v1 is a deliberately minimal schema). Mitigation sketch: state the
supply-observability property explicitly; document the continuity limit as a known v1 boundary and
name issuer-succession/multi-sig as a required v2 feature for any non-toy asset.

## Rejected candidates

| Candidate | Honest reason for rejection |
|---|---|
| **Inclusion-ordering fairness / MEV-analogue (publisher chooses batch composition + ordering; `prev_root` serialises a single writer)** | Within a batch, ordering is **value-neutral by construction**: every member nullifier is inserted into the SMT and order does not change any member's outcome (`SMT.insert_many` is commutative on the set), so there is no in-batch front-running surface. Cross-batch, the `prev_root` race is decided by Bitcoin's own fee market (threat-model S5), which the spec correctly classifies as *endemic to Bitcoin, accepted as residual*. The one residual — a publisher griefing competitors by stale-forcing their batches — is real but is the same liveness/censorship concern already captured under **P11**, not a separate property. No theft, no privacy, no novel zkCoins-specific MEV beyond inherited Bitcoin fee-market behaviour. |
| **Recovery liveness after operator/node switch** | This is exactly the **P9 liveness half**, already explicitly recorded as *not* verified (enabledness surrogate; MEDIUM label; depends on `k` and operator independence). It is honestly scoped, not silently missing — so it is a known *open* item, not an *unstated* gap. (Its DA precondition is sharpened by P12; its censorship-of-pull cousin is P11.) |
| **Privacy-vs-backup trade-off across `k` replicas (what k operators learn over time, cross-replica traffic analysis)** | Already covered by the *stated bound* of P5 (on-chain) and P8 (transport): each replica holds only NIP-44-ciphertext + per-coin all-distinct `detect_tag`s and learns "an opaque blob was stored," with the network-layer/long-run-intersection residual explicitly placed *out of scope* (P5 MEDIUM, deferred to operational hygiene + the OPTIONAL FMD upgrade). The trade-off is real but it is the *acknowledged ceiling* of P5/P8, not an unstated property — promoting it would restate an existing MEDIUM, not fill a hole. |
| **Fee / economic-soundness of publisher compensation (off-chain MAY)** | The economic *liveness* consequence (no fee ⇒ no publisher ⇒ no inclusion) is fully absorbed by **P11** (censorship/inclusion), which is where the user harm actually lands; there is no distinct *safety* property at stake because §3.8 makes fee policy non-consensus and publishing permissionless, so no publisher can extract rent or corrupt state by fee manipulation. Folding it into P11 avoids a near-duplicate. |
| **Protocol upgrade / versioning safety (v1→v2 migration)** | **Partially covered, honestly bounded.** P7 + §6.5 prove cross-version *coin* distinctness is structural (version bound into `asset_id`), and the cyclic-recursion constraint forces the single-circuit-version-branch dispatch — the spec reasons about this correctly. What is *not* a property is *network/consensus* upgrade safety (how the scanning network coordinates a circuit/verifier-data change without a split) — but that is a future-version concern with no v1 surface to verify, and F15 (canonical verifier-data designation) already gates it as the structural deployment blocker. Genuinely premature to state as a v1 property; noted as a v2 watch-item rather than a v1 gap. |
| **Replay / payment-replay** | Threat-model S4: the nullifier mechanism gives **protocol-level immunity** (a replayed spend's `nf` is already in the accumulator). Application-level link reuse is a UX matter, not a protocol property. Fully covered by P2. |

## Recommendations (priority order)

1. **`R-D1-1` (P11, HIGH): make censorship-resistance a first-class, honestly-costed property.**
   This is the gap that most threatens the "censorship-resistant money" claim. State a
   self-publication *enabledness* invariant (formally checkable) **and** specify a real, costed
   emergency self-publish path for thin clients without an existing BTC UTXO. Without this, the
   protocol's censorship story is "be a whale," and that should be said out loud if it cannot be
   fixed.
2. **`R-D1-2` (P12, HIGH): elevate accumulator data-availability to a stated property and specify
   persistent-unavailability behaviour.** The network's only consensus object depends on off-chain
   data; "the chain can fork on DA loss" is in the spec as prose but not as a guarded property.
   Define verifier behaviour on *persistently* unavailable bundles and add an incentivised archival
   role for `BatchBundle`s (which, unlike `CoinProof` bundles, have no natural long-term holder).
3. **`R-D1-3` (P13, MEDIUM–HIGH likelihood): turn "wallet halts, user resolves" into a real
   guarantee.** State the detection property, specify a deterministic loss-free fork-resolution
   procedure, and add a pre-spend freshness gate. Multi-device-on-one-seed is supported and common;
   the current answer is detection-then-manual, which is viable only for experts.
4. **`R-D1-4` (P14, MEDIUM): define proof-of-payment honestly.** Promote the `ack_nonce`-bound ACK
   to a portable, third-party-verifiable receipt, and state plainly that proof-of-*receipt* is
   impossible without recipient cooperation — so the §5.6 "verifiable proof I sent it" line is
   backed by a property, not a slogan, and the S8 withhold / S2 equivocation asymmetries are named.
5. **`R-D1-5` (P15, MEDIUM/LOW): state supply-observability as a property and document the v1
   issuer-continuity boundary.** P3 silently assumes honest issuance accounting; make the
   observability that backs "supply discipline" a checkable property, and name issuer
   succession/multi-sig as a required feature for any non-toy asset.

## Bottom line

**Risk count: 5 accepted gaps (R-D1-1 … R-D1-5).**

| ID | Property | Severity | Likelihood | Formal vs operational |
|---|---|---|---|---|
| R-D1-1 | P11 Censorship/inclusion-resistance of spends | HIGH | MEDIUM | operational (weak enabledness form formal) |
| R-D1-2 | P12 Accumulator DA / progress-verifiability | HIGH | LOW–MEDIUM | hybrid (admission formal, availability operational) |
| R-D1-3 | P13 Multi-device single-seed consistency | MEDIUM | MEDIUM–HIGH | partly formal (recovery half operational) |
| R-D1-4 | P14 Receiver non-repudiation / proof-of-payment | MEDIUM | MEDIUM | mostly operational (ACK-binding core formal) |
| R-D1-5 | P15 Issuer continuity + supply observability | MEDIUM (cont.) / LOW–MED (obs.) | LOW–MEDIUM | observability formal, continuity operational |

**Headline findings.**

1. **P1–P10 is a safety set verifying an incomplete set of goals.** It proves the protocol cannot
   lie or steal; it proves almost nothing about whether the user can *transact, include a spend,
   stay consistent across devices, or get included at all*. Every D1 gap is a *liveness/contention*
   goal that was never stated — and a goal never stated can never be mis-stated, so it slips past M4
   into M3 (adversary/goal-model completeness) unflagged.
2. **The strongest claim in the brand — "censorship-resistant" — is the weakest in the property
   set (R-D1-1).** Permissionless self-publish is a cost shift onto the user (proving cost + a
   privacy-puncturing BTC UTXO + a publisher race), not a guarantee; a thin client facing a
   publisher cartel can hold funds safely but cannot spend them.
3. **Post-Variant-2, network consensus liveness now rests on off-chain `BatchBundle` availability
   (R-D1-2),** and the spec itself names the resulting fork-on-DA-loss — yet "the accumulator's
   progress is verifiable by anyone at any time" is not a stated property, and `BatchBundle`s
   (unlike `CoinProof` bundles) have no naturally-incentivised long-term holder.
4. **Multi-device consistency is detection, not prevention (R-D1-3),** and the more common real
   failure is *silent staleness* (a device that missed a self-delivered change bundle), which only
   becomes a detectable fork *after* an unsafe spend is attempted.
5. **Neither payer nor payee can hold the other accountable (R-D1-4):** the system markets
   "verifiable proof I sent it" but states no non-repudiation property, while the threat model
   already records sender-withhold (S8) and sender-equivocation (S2) with "reputation is the only
   deterrent."

**Honest one-line answer.** No — as verified, P1–P10 do **not** on their own support a "concept is
sound" claim: they soundly establish that zkCoins cannot be made to *forge, double-spend, or leak*,
but they are silent on whether a user can *reliably transact, get included, stay consistent across
their own devices, prove a payment, or rely on the network's consensus object remaining verifiable*
— and at least two of those gaps (censorship/inclusion and accumulator data-availability) are
fundamental, not operational polish.
