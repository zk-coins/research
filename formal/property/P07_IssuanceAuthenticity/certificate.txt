What the model proves
---------------------
property.tla EXTENDS module/Proofs.tla -- the faithful conjunction of the nine
Sec. 2.1 compliance clauses C and the per-account issuance/spend state machine
PrInit/PrNext. The §6.5 v1 mint clauses (a)-(d) are Proofs.MintV1Clauses, gated
into Clause3_Balance when an issuance is present. The only minting action is
MintStep (an InitialProof, sendCounter = 0) signing under the account's own
current key (the A7 oracle prAuthorised grows only by an account signing its own
transition); SendStep never mints. The invariant added here:

  INV_P7 == \A a \in Accounts :
              /\ \A x   \in DOMAIN prState[a].balances : x.creator        = AddressOf(a)
              /\ \A cid \in prChSet[a]                  : cid.asset.creator = AddressOf(a)

In this machine the account index `a` is its own Pk0 and owner
(CanonicalEmptyAccount(a, a); AddressOf(a) = a), so "asset present in account a
=> its creator = a" IS issuance authenticity: an asset's coins live only in the
balances/coin-history of its single creator account, and only that account ever
minted it.

What "unbounded" means here
---------------------------
The proof removes any execution-length bound: the conjunction of checks
[2] (base), [3] (step) and [4] (implication) is a standard inductive-invariant
argument, so INV_P7 holds in EVERY reachable state of PrInit/PrNext, for an
arbitrary number of MintStep/SendStep transitions. The account universe is a
finite parameter (Accounts = {1,2}); the inductive argument is per-account local
(each IndInv conjunct quantifies a single account and every action touches one
account) and uniform in |Accounts| -- the base [2] and implication [4] checks
were re-confirmed at Accounts = {1,2,3} (notes.md). Data-domain finiteness per
state is intrinsic to SMT-based model checking and is recorded as a modelling
parameter, not a hidden bound on the number of transitions.

Inductive invariant and strengthenings
---------------------------------------
INV_P7 alone is NOT inductive (MintStep builds AssetOf(prev.current_pubkey)).
The closing inductive invariant is

  IndInv == PrTypeOK
            /\ \A a \in Accounts : OwnerPinned(a) /\ FreshIsCanonical(a)
            /\ INV_P7

with two strengthenings:
  S1 (OwnerPinned)      prState[a].owner = AddressOf(a)            [PrInit + clause 7]
  S2 (FreshIsCanonical) sendCounter = 0 => current_pubkey = a
                        AND balances empty AND coin-history empty
S2 is what MintStep relies on to mint a's OWN asset, and what makes a second
mint impossible (after a mint, sendCounter > 0, disabling MintStep).
IndInvInit is the assignment-form `--init` for the step check: each variable is
produced by apalache.Gen and pinned by the IndInv body (an explicit
set-of-functions carrier for prState would force Apalache to expand a set of
functions). It is logically equivalent to IndInv.

Negative control (the §6.5 (b)/(c) clauses are load-bearing)
------------------------------------------------------------
In a /tmp copy, MintV1Clauses was weakened by DROPPING conjunct (b)
AddressOf(creator_pubkey) = prev_account_state.owner, and a foreign-mint action
MintForeignStep(a, creatorPk, amount) was added to PrNext: account `a` performs
a v1 InitialProof for AssetOf(creatorPk) -- a possibly different account's asset
-- signing under its OWN current key (no signature forgery; the A7 oracle stays
honest). Running

  apalache-mc check --cinit=ConstInit --init=PrInit --next=PrNext --inv=INV_P7 --length=2 property.tla

yields a counterexample at State 1 (EXITCODE 12, "state invariant violated"):

  Accounts = {1, 2}
  prAuthorised = { <<2, (message handle)>> }                 (account 2 signed, under its own key Pk=2)
  prState[2]   = [ owner |-> 2, currentPk |-> 3, sendCounter |-> 1, ... ]
  prChSet[2]   = { [ asset |-> [creator |-> 1, version |-> 1, ...], idx |-> 1, ... ] }
               => account 2 (owner 2) holds a coin whose asset.creator = 1
               => INV_P7 (CoinsAuthentic(2)) violated: a NON-creator minted
                  account 1's asset.

With conjunct (b) intact, the mint forces creator_pubkey = owner = a, so the
counterexample disappears and the four checks above all report NoError --
confirming the model can SEE an authenticity violation, so the verified verdict
is meaningful. (Dropping conjunct (c), the asset_id derivation, yields the same
class of violation.) The committed property.tla / module/Proofs.tla keep all
four §6.5 clauses intact.

Cross-check vs Pass-3
---------------------
Pass-3 label HIGH (for v1); Apalache verdict VERIFIED => confirmed at the
compliance-predicate level. The clauses the audit's attack-class enumeration
leans on (fake creator_pubkey witness; witnessed-Pk0 vs signed-under-Pki
discrepancy) are exactly the ones the negative control shows to be load-bearing
(clause (b) + clause 2's txn_sig + clause 7's owner-invariance = S1). Full
reconciliation is deferred to Phase 4.

Scope
-----
- Cross-version replay (v1 vs v2 asset_id distinctness) -- the audit's third
  attack class -- is STRUCTURAL in Foundations.MkAssetId: asset_id carries a
  `version` field, so a v2 mint of "the same" asset is a different asset_id
  value (distinct records under A3). The model fixes version = IssuanceVersionV1
  everywhere, so v1/v2 non-confusion holds by construction and needs no separate
  invariant; it becomes a live check only when a v2 schema is added
  (single-circuit version branch, §6.5 Forward compatibility).
- In-circuit SHA-256 preimage resistance (A6) for H(creator_pubkey) is an axiom
  (Assumptions), modelled at the AddressOf-image level.
- The publisher / on-chain layer is out of scope for P7 (covered by P2);
  authenticity is enforced in the per-account proof before any SpendRecord
  reaches a publisher.
