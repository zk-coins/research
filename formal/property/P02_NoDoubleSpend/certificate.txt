--------------------------------------------------------------------------------
"UNBOUNDED" and the Seq variable (honest scope)
--------------------------------------------------------------------------------
The unbounded claim is the no-double-spend SAFETY property. IndInv_P2 is stated
over the SET variables (onPending/onCompleted/onDoubled/onAuthorised); it does
not reference the `onAdmittedChain` SEQUENCE. The inductive step [B3] uses an
assignment-form init (IndInvInit) that ASSIGNS every Onchain variable, drawing
each set from its powerset and assigning the sequence an arbitrary value via
apalache.Gen (capacity <= 4). Because IndInv_P2 never reads the chain, and the
SET effects of every OnNext action (incl. Admit, which Appends to the chain) do
not depend on the chain's value, the step is a faithful statement about the SET
PROJECTION of the state: "for every reachable set-state satisfying IndInv_P2
(under ANY admitted history), one OnNext step preserves IndInv_P2." The Gen
capacity bounds only the bookkeeping witness, never the safety conclusion. The
[GATE] tests batch nullifiers against the live set `Acc`, not the chain, so the
set-projection proof is a complete proof of the P2 claim -- the chain is pure
bookkeeping.

Chain prev_root continuity DOES quantify over DOMAIN onAdmittedChain. Apalache
encodes a Seq with a static capacity, so an unbounded inductive step assuming a
continuity-respecting chain of arbitrary length is not one SMT query. We are
explicit: continuity is verified BOUNDED (length 6), and only over the
admit/confirm fragment -- see the next section.

--------------------------------------------------------------------------------
Honest finding -- Reorg breaks prev_root continuity (over-approximation)
--------------------------------------------------------------------------------
OnPrevRootContinuity is NOT an invariant of the FULL machine including Reorg.
Onchain's `Reorg` rebuilds the chain with SelectSeq(onAdmittedChain, Survives),
which removes reverted batches WHEREVER they sit. The module comment intends a
SUFFIX-only revert, but the coded SelectSeq over an arbitrary D \subseteq
onPending over-approximates to any-position removal; a surviving later batch
then keeps a prev_root that commits to a now-removed predecessor, breaking local
continuity. This is a chain-bookkeeping over-approximation in Reorg, NOT a
safety violation: no-double-spend is tested against the live set accumulator,
holds under Reorg (proven [B2]+[B3]+[B4]), and does not lean on continuity.
Continuity is therefore certified over the admit/confirm fragment ([B5]); the
gap is documented in notes.md ("Reorg continuity over-approximation"). Onchain
was NOT modified.

Negative control on Layer C (the member_root ORDER binding is load-bearing)
--------------------------------------------------------------------------------
The committed companion member_root_nc.tla replaces the order-sensitive
MemberRoot with the order-INSENSITIVE set-hash
MemberRootSet(seq) == { seq[i] : i \in DOMAIN seq } (member_root = the member SET
only -- the order binding is DELETED), checked with
  apalache-mc check --cinit=ConstInit --init=Init --next=Next --inv=LocatorBindsOrder --length=2 member_root_nc.tla
yields a counterexample (The outcome is: Error, exit 12). 2-step trace:
  State1  admit  memberSeq = <<3,2>>, locator.mr = {2,3}   (one ordering)
  State2  admit  memberSeq = <<2,3>>, locator.mr = {2,3}   (the OTHER ordering)
          => two distinct permutations share a member_root but differ as
             sequences => LocatorBindsOrder violated.
So the SAME invariant becomes FALSE the moment the order binding is removed --
the definitive proof it has real content. The committed member_root.tla is
unchanged; the negative-control _apalache-out was discarded.
