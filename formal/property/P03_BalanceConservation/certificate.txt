CERTIFICATE -- P03 Per-Asset Balance Conservation
================================================================================

Property      : P03 Per-Asset Balance Conservation.
Claim         : For every asset `a`, the live supply of `a` (total value of all
                unspent coins of `a` held across every account) never exceeds the
                cumulative Mint(a) produced by valid v1 issuance transitions.
                Outputs never exceed inputs plus an explicit, predicate-checked,
                creator-bound Mint; held value is never created except by a Mint
                that the compliance predicate C (Sec. 2.1 clause 3 + the Sec. 6.5
                v1 clauses) authorises.  (Pass-3 audit P3, HIGH.)
                NOTE: v1 supply is CREATOR-BOUND, not protocol-capped (Sec. 6.5:
                "supply discipline is a creator's commitment, not a protocol
                guarantee"). P3 is the no-inflation inequality, NOT a ceiling.
Result        : VERIFIED -- unbounded, via inductive invariant over the
                per-account compliance state machine module/Proofs.tla.

Tool          : Apalache 0.58.0  (build 711dce6; SMT backend: Z3 4.14.1.0)
Host          : Apple Silicon (arm64), macOS (Darwin 25.5.0)

--------------------------------------------------------------------------------
WHAT IS PROVEN
--------------------------------------------------------------------------------
property.tla EXTENDS the full per-account compliance machine module/Proofs.tla:
the nine-clause compliance predicate C (Sec. 2.1), the v1 InitialProof mint and
AccountUpdateProof send actions, the A7 signing oracle, and the per-account,
per-asset balance bookkeeping. Every transition is admitted ONLY when C holds,
so Sec. 2.1 clause 3 (In(a) + Mint(a) >= Out(a)) is enforced on every step by
construction.

P3 quantifies live supply against TOTAL MINTED -- a history-dependent quantity
that is NOT recoverable from the machine's state (a coin's value is private
witness data, Sec. 2.1 clause 9; the per-account coin-history set stores coin
IDs, not amounts). A property module may not redefine PrNext's assignments, so
this module defines its OWN thin state machine that:
  (i)   reuses every Proofs datatype, helper, and the predicate C verbatim;
  (ii)  drives the SAME two C-gated actions with the SAME prState / prChSet /
        prAuthorised updates as Proofs.MintStep / Proofs.SendStep;
  (iii) adds two GHOST ledgers, both per asset:
          prSupply[a] -- live coin value (sum of unspent coin amounts);
          prMinted[a] -- cumulative Mint(a) over admitted v1 issuances.
        A mint raises BOTH by exactly the issued amount; a self-conserving send
        (In(a) = Out(a)) leaves both unchanged. The ghosts are observational
        only -- they never gate a transition -- so the reachable prState behaviour
        is identical to Proofs'; they only make the mint history observable so
        conservation can be stated and proven inductively.

Conservation invariant:  \A a \in AssetCarrier : prSupply[a] <= prMinted[a].

The unbounded proof is the standard inductive-invariant argument [2]+[3]+[4]:
  [2] base        P3Init  => IndInv
  [3] step        IndInv /\ P3Next => IndInv'
  [4] implication IndInv  => Conservation
=> Conservation holds in EVERY reachable state, for an arbitrary number of mint
   and send transitions. [1] is a supporting bounded reachability sanity pass.

IndInv == PrTypeOK /\ MintedTypeOK /\ Structural /\ Conservation, where:
  - PrTypeOK    -- the EXACT typing predicate of module/Proofs.tla (shared);
  - MintedTypeOK-- both ghost ledgers total over the asset carrier and >= 0;
  - Structural  -- owner = a always (clause 7 never changes it), and a
                   send_counter = 0 account still has current_pubkey = a, so the
                   only mint it can perform creates an asset whose creator a is
                   in Accounts (in AssetCarrier). This reachability fact is what
                   PrTypeOK alone does not give and is what closes the induction
                   (see notes.md strengthening log).

NEGATIVE CONTROL -- clause 3 is load-bearing
--------------------------------------------------------------------------------
In a /tmp staging copy, the per-asset conservation conjunct of
Proofs.Clause3_Balance was DELETED:

    \A a \in AssetsTouched(w) : InAmount(w.inputs,a) + MintAmount(w,a)
                                  >= OutAmount(w.templates,a)        <-- removed

and an INFLATING send action was added to the property machine: it spends one
held coin of `amount` but emits a change coin of `amount + extra` (extra > 0) of
the same asset (Out(a) > In(a), Mint(a) = 0), with the ghost prSupply truthfully
raised by `extra`. Honestly this transition is rejected by C; with clause 3
deleted, C admits it. Running:

  apalache-mc check --cinit=ConstInit --init=P3Init --next=P3Next \
                    --inv=Conservation --length=4 property.tla

  # APALACHE version: 0.58.0 | build: 711dce6
    > Found 1 initializing transitions
    > Found 3 transitions
  State 2: state invariant 0 violated.
  Found 1 error(s)
  The outcome is: Error
  Total time: 3.233 sec

Counterexample (per-asset ghost values, asset = the v1 family of account 2):
  State0:  prSupply = 0,  prMinted = 0        (initial)
  State1:  prSupply = 1,  prMinted = 1        (account 2 mints 1)
  State2:  prSupply = 2,  prMinted = 1        (inflating send: spend 1, emit 2)
           => Conservation  prSupply[a] <= prMinted[a]  violated (2 > 1):
              one unit of asset created out of thin air.

So a NoError verdict WITH clause 3 is meaningful: the model can see inflation,
and the conservation conjunct of C is exactly what rules it out.
